Service sandbox

Local stand-ins for the outside services one-ngo calls. Each capability below names the production system it replaces, what the stand-in does, and how to connect it to the NGO app or the operator console.

13capabilities
8095default HTTPS port
2525default SMTP port
Localthis machine only

For local development and tests only. Every service answers on this machine with fixed demo credentials. Nothing here talks to a real Razorpay, Cashfree, Google, Cloud Storage, or Have I Been Pwned account.

Start it

npm run dev from the repository root starts the sandbox on HTTPS 8095 and SMTP 2525, waits until it answers, then starts the API, the web app, and the operator console. Pass --no-web or --no-console to leave one out. Prepare the database once with npm run dev:setup. The examples on this page use the default ports. Files stay in .data/service-sandbox.

To run the sandbox alone, use npm run demo:integrations from the repository root, or npm run dev in apps/service-sandbox/server. Pass --https-port and --smtp-port to change its ports.

The sandbox home page is https://127.0.0.1:8095/. It shows the settings block, orders, mail, and a log. /api/log returns the same log as JSON. The browser warns about the certificate once; accepting it covers that session, and the API trusts the same certificate through NODE_EXTRA_CA_CERTS.

Capability details

Open a capability to see which production system it stands in for, what it does, and how to connect it. The API npm run dev script sets the environment each section names, using sandbox port 8095. Pass --fixture-port to the API and the console when the sandbox is on another port.

Google sign-inSign-inSave in app

Production system

Google OpenID Connect at https://accounts.google.com, the default member sign-in issuer. Any other OpenID Connect issuer set as OIDC_ISSUER works the same way, and the host rewrite does not touch Google. npm run dev sets OIDC_ISSUER to the sandbox.

What it does

Stands in for that issuer on the sandbox origin. It serves discovery at /.well-known/openid-configuration, the sign-in page at /oauth2/authorize, the code exchange at /oauth2/token, and the signing keys at /oauth2/jwks. The sign-in page asks only for an email. The ID token marks that email verified, and its subject is demo- plus the first 20 hex characters of the SHA-256 of the lower-cased email. An authorization code lasts 5 minutes and the ID token lasts 1 hour. The sandbox does not create a member.

How to integrate it

npm run dev sets OIDC_ISSUER to the sandbox, OIDC_CLIENT_ID=demo-google, OIDC_CLIENT_SECRET=demo-google-secret, OIDC_PROVIDER_ID=google, OIDC_PROVIDER_LABEL=Google, and NODE_EXTRA_CA_CERTS. In the operator console, open the organisation's sign-in settings and turn on the shared Google provider for that organisation. Then open the organisation sign-in page in the NGO app and choose Google.

On the sandbox page, enter the email of a member who already exists in that organisation. one-ngo refuses an email it does not already have.

Operator sign-inSign-inReady

Production system

The operator console's identity provider. Production uses an external provider that can prove multi-factor sign-in, and Auth0 is the one named for that role. Google used on its own is not accepted for operators. OPERATOR_OIDC_ISSUER holds the provider's address, and npm run dev points it at the sandbox.

What it does

Uses the same OpenID Connect endpoints as Google sign-in, with a second client: id and audience demo-operator, secret demo-operator-secret. The ID token includes amr values of pwd and mfa, which the operator console requires. The page does not ask for a password or a second factor; it writes those claims itself. The console still decides what the person may do, so a token for an email that was never linked does not create a session.

How to integrate it

The console npm run dev script sets OPERATOR_OIDC_ISSUER, OPERATOR_OIDC_CLIENT_ID, OPERATOR_OIDC_CLIENT_SECRET, and OPERATOR_OIDC_AUDIENCE. npm run dev:setup links one account, display name "Local operator", to operator.full@onengo.local and grants every console action.

Open http://localhost:9090, then enter operator.full@onengo.local on the sandbox page. A different email produces a different subject, and the console finds no account for it.

RazorpayPaymentsSave in app

Production system

The Razorpay Orders API at https://api.razorpay.com. Production calls that host. RAZORPAY_API_BASE replaces it with the sandbox, and the host rewrite does not touch Razorpay.

What it does

Stands in for order creation at POST /v1/orders. It accepts HTTP basic auth with key id rzp_test_demo and key secret demo-key-secret, requires an amount of at least 100 paise and the currency INR, and rejects any other key. Orders are kept in memory and listed on the sandbox home page; restarting the sandbox clears them. Capture posts a payment.captured webhook and Fail posts payment.failed. Both are signed with demo-webhook-secret.

How to integrate it

npm run dev sets RAZORPAY_API_BASE to https://127.0.0.1:8095. Then, as a member who can manage payment gateways such as a treasurer, save the gateway with PUT /api/admin/payment-gateways/razorpay:

{ "keyId": "rzp_test_demo", "keySecret": "demo-key-secret", "webhookSecret": "demo-webhook-secret" }

Start a payment in the NGO app. The order appears on the sandbox home page with its amount and reference. Leave the organisation box as demo, or type another organisation key such as harbour, and click Capture or Fail. The sandbox posts to http://localhost:<backend port>/webhooks/payments/razorpay/<org>. The order status changes only when one-ngo answers with a success status, and the home page log records the result.

CashfreePaymentsSave in app

Production system

Cashfree at https://sandbox.cashfree.com when the saved environment is sandbox, which is the default, and https://api.cashfree.com when it is production. CASHFREE_API_BASE replaces both hosts with the sandbox, and the host rewrite does not touch Cashfree.

What it does

Stands in for order creation at POST /pg/orders. Requests must carry x-client-id: cf_demo, x-client-secret: demo-cf-secret, and an x-api-version header, and the amount must be at least 1 rupee in INR. As with Razorpay, Capture and Fail on the home page post a webhook signed with the client secret, and the order status changes only when one-ngo answers with a success status.

How to integrate it

npm run dev sets CASHFREE_API_BASE to the sandbox origin. Save the gateway with PUT /api/admin/payment-gateways/cashfree:

{ "keyId": "cf_demo", "keySecret": "demo-cf-secret", "environment": "sandbox" }

Start a payment in the NGO app, then click Capture or Fail on the sandbox home page. The webhook goes to http://localhost:<backend port>/webhooks/payments/cashfree/<org>, so set the organisation box to the key that owns the payment. The home page log records the answer or a connection error.

EmailMessagingReady

Production system

The installation's SMTP server, whatever SMTP_HOST names. The product does not name a mail vendor, and the usual production port is 587. npm run dev points SMTP_HOST and SMTP_PORT at this listener.

What it does

Accepts SMTP on 127.0.0.1 and the SMTP port, without TLS. The login is demo / demo, AUTH PLAIN and AUTH LOGIN both work, and the From address is demo@localhost. Each message is kept in memory, up to 10 MB, and listed on the sandbox home page. GET /mail/<id> returns the raw source. Restarting the sandbox clears the mailbox.

How to integrate it

npm run dev sets SMTP_HOST, SMTP_PORT, SMTP_SECURE=0, SMTP_USER, SMTP_PASSWORD, and SMTP_FROM on the API. Nothing is saved in the app. Do something in the NGO app that sends mail, such as an invitation or a password reset, then open the sandbox home page and click the message. Nothing reaches a real inbox.

SMSConnectorsSave in app

Production system

The HTTPS SMS gateway saved on the organisation's sms connector. one-ngo does not call a named SMS vendor, so the connector URL is the production system. When you leave the sandbox, point that URL at the real gateway; the same {{to}} and {{message}} placeholders apply.

What it does

POST /sms accepts a JSON body and returns a queued id such as sms_…. The request must send Authorization: Bearer demo-sms-key, and a wrong key is refused. Every send is written to the sandbox log.

How to integrate it

npm run dev adds 127.0.0.1 to CONNECTOR_ALLOWED_HOSTS, and the API refuses to call this address without it. In the NGO app, open Administration → Connectors, create a connector with key sms, and save this definition:

{
  "kind": "sms",
  "enabled": true,
  "config": {
    "url": "https://127.0.0.1:8095/sms",
    "method": "POST",
    "headers": { "Authorization": "Bearer {{secrets.apiKey}}" },
    "body": "{\"to\":\"{{to}}\",\"message\":\"{{message}}\"}",
    "contentType": "json"
  },
  "secrets": { "apiKey": "demo-sms-key" }
}

Use that connector from the feature that sends SMS. The sandbox log shows the body it received.

WhatsAppConnectorsSave in app

Production system

The WhatsApp Business Cloud API. In production, baseUrl is that API's address including its version, and phoneNumberId comes from WhatsApp Business. The sandbox uses phone number id 1234567890 and token demo-whatsapp-token in place of those production values.

What it does

Stands in for a Cloud API send at POST /whatsapp/1234567890/messages. A request with Authorization: Bearer demo-whatsapp-token returns a wamid.demo… id, and a wrong token is refused. The sandbox log shows the recorded body.

How to integrate it

Confirm 127.0.0.1 is in CONNECTOR_ALLOWED_HOSTS; npm run dev adds it. In Administration → Connectors, create key whatsapp and save this definition:

{
  "kind": "whatsapp",
  "enabled": true,
  "config": {
    "baseUrl": "https://127.0.0.1:8095/whatsapp",
    "phoneNumberId": "1234567890"
  },
  "secrets": { "accessToken": "demo-whatsapp-token" }
}

Send a WhatsApp message from the NGO app and check the sandbox log.

WebhookConnectorsSave in app

Production system

The HTTPS receiver the organisation names on a webhook connector. That is the customer's own endpoint, or any service that checks x-ngo-signature. one-ngo signs the raw body with the connector's signing secret, and the sandbox checks that same signature.

What it does

POST /hooks/in receives outbound webhooks from one-ngo. It reads the header x-ngo-signature, which must be sha256= followed by the HMAC-SHA256 of the raw body with demo-signing-secret. A match returns success and any other signature is refused. Both outcomes are written to the sandbox log, along with the event name.

How to integrate it

Confirm 127.0.0.1 is in CONNECTOR_ALLOWED_HOSTS. In Administration → Connectors, create key webhook and save this definition:

{
  "kind": "webhook",
  "enabled": true,
  "config": { "url": "https://127.0.0.1:8095/hooks/in" },
  "secrets": { "signingSecret": "demo-signing-secret" }
}

Trigger the event in the NGO app that calls this connector, then check the sandbox log.

Pincode lookupConnectorsSave in app

Production system

An HTTPS lookup the organisation saves on an http connector in lookup mode. one-ngo does not call a postal service itself, so the connector URL is the production system. This stand-in answers four India PIN codes so a record can fill its area and district. A production lookup, such as a bank or postal API, fills its own fields from its own address.

What it does

GET /lookup/<pincode> returns {"data":{"code","name","district","state"}} for the four PIN codes below. Any other PIN code returns 404.

PIN codeAreaDistrictState
110001Connaught PlaceNew DelhiDelhi
400001FortMumbaiMaharashtra
560001Bengaluru GPOBengaluru UrbanKarnataka
700001BBD BaghKolkataWest Bengal

How to integrate it

Confirm 127.0.0.1 is in CONNECTOR_ALLOWED_HOSTS. In Administration → Connectors, create key pincode and save this definition. The response map copies data.name to area and data.district to district.

{
  "kind": "http",
  "enabled": true,
  "config": {
    "mode": "lookup",
    "method": "GET",
    "url": "https://127.0.0.1:8095/lookup/{{record.pincode}}",
    "inputs": ["pincode"],
    "responseMap": { "area": "data.name", "district": "data.district" }
  }
}

On a record that uses this lookup, enter one of the PIN codes above. A code outside the table comes back as not found.

Connector OAuthConnectorsSave in app

Production system

The OAuth authorization-code provider named on an oauth connector, with that connector's authorizationUrl and tokenUrl. For Google those are https://accounts.google.com/o/oauth2/v2/auth and https://oauth2.googleapis.com/token. The sandbox consent page stands in for that provider.

What it does

/connector-oauth/authorize shows Allow and Deny for scope demo.read, with client id demo-connector and secret demo-connector-secret. /connector-oauth/token exchanges the code, or a refresh token, for an access token. A code lasts 5 minutes and an access token lasts 1 hour. Deny returns access_denied and no token.

How to integrate it

Confirm 127.0.0.1 is in CONNECTOR_ALLOWED_HOSTS. In Administration → Connectors, create key demoOauth and save this definition:

{
  "kind": "oauth",
  "enabled": true,
  "config": {
    "authorizationUrl": "https://127.0.0.1:8095/connector-oauth/authorize",
    "tokenUrl": "https://127.0.0.1:8095/connector-oauth/token",
    "clientId": "demo-connector",
    "scopes": ["demo.read"]
  },
  "secrets": { "clientSecret": "demo-connector-secret" }
}

Start the connector's connect action in the NGO app. On the sandbox consent page, click Allow.

Cloud StorageFiles.env

Production system

The Google Cloud Storage JSON API at storage.googleapis.com. With INTEGRATION_FIXTURE_ORIGIN set, the API rewrites those calls to the sandbox. A deployment never sets that variable, so production talks to Cloud Storage.

What it does

Stands in for that API for upload, metadata, download, and delete. Objects are stored as files under .data/service-sandbox/<fixture port>/files/<bucket>/ and survive a restart. Calls must send the bearer token demo-gcs-token, which the metadata token endpoint hands out.

How to integrate it

Set FILE_STORE_BUCKET in .env. FILE_STORE_PREFIX is optional. Without a bucket, the API keeps files on local disk and does not call this stand-in. npm run dev sets INTEGRATION_FIXTURE_ORIGIN, which rewrites calls to storage.googleapis.com to the sandbox.

Restart the dev stack after changing .env, then upload or download a file in the NGO app. The sandbox log names the bucket, object, and size.

Metadata tokenFilesReady

Production system

The Compute Engine metadata server at metadata.google.internal, path /computeMetadata/v1/instance/service-accounts/default/token. The host rewrite sends that path to GET /token on the sandbox. On App Engine or Compute Engine, production receives a real token from that host.

What it does

GET /token with the header Metadata-Flavor: Google returns {"access_token":"demo-gcs-token","expires_in":3599,"token_type":"Bearer"}. A request without the header is refused.

How to integrate it

Nothing to save in the app. npm run dev sets INTEGRATION_FIXTURE_ORIGIN, and the API then sends its metadata token request here. Upload a file after FILE_STORE_BUCKET is set; the sandbox log shows "Metadata token issued" before the object is stored.

Breached passwordsSecurityReady

Production system

Have I Been Pwned's Pwned Passwords range API at https://api.pwnedpasswords.com/range/<5 hex characters>. The host rewrite sends only /range/… to the sandbox, so with the check left on, production calls Have I Been Pwned.

What it does

GET /range/<5 hex characters> answers in the same SUFFIX:COUNT line format. Only the exact word password is reported breached, and every other password is reported clear.

How to integrate it

Leave BREACHED_PASSWORD_CHECK unset or set it to online. npm run dev rewrites api.pwnedpasswords.com/range/… to the sandbox through INTEGRATION_FIXTURE_ORIGIN. Set or change a password in the NGO app: password is refused as breached, and any other password passes this check. To skip the check, set BREACHED_PASSWORD_CHECK=off in .env and restart the API.

Troubleshooting

ProblemWhat to do
Certificate warning in the browserAccept it once for the sandbox page and the sign-in page. The API trusts the same certificate through NODE_EXTRA_CA_CERTS.
Port already in useStop the process using that port, or pass another one. The sandbox takes --https-port and --smtp-port. The API, web app, and console take --port.
Operator sign-in creates no sessionEnter operator.full@onengo.local. A different email does not match the one account npm run dev:setup linked.
Sign-in, payments, or files fail after a manual startStart one-ngo with the settings from the sandbox home page. Without INTEGRATION_FIXTURE_ORIGIN, Cloud Storage and breached-password calls go to the real services.
Start from clean dataStop the sandbox and delete .data/service-sandbox. The next start creates new certificates and files. Mail and orders were only in memory.

Keep the organisation's saved credentials and the sandbox values in step. If you change a secret in one place, change it in the other.
