OneNGO: one place for an NGO's people, records, and money

OneNGO is a configurable management platform for non-profits. Donations, members, expenses, approvals, and receipts all live in one app that an NGO sets up for itself, without waiting for a developer. This page is the front door. It explains the product in plain words and points you to the right guide.

What is OneNGO?

Most small NGOs run on spreadsheets, or on software that needs a developer for every change. OneNGO gives them a single app where donors, members, money, and approvals sit together. The app is configurable: an administrator adds a form, a rule, or an approval step in a screen called the Builder, and it is live. No developer, no release.

The problems it solves

Change without waitingNew fields, rules, approval steps, and pages are made by the NGO itself in the Builder.
Cost that fits a small NGOOne light server that sleeps when idle and runs mostly within a free cloud allowance. No paid cache or queue.
Trustworthy accountsEntries balance, receipt numbers are never reused, and a closed year stays closed. Configuration cannot bend these.
Two ways to run it

A one-NGO installation gives an NGO its own project and database, so it holds its own data. A shared installation hosts many NGOs side by side, each kept apart by the database itself. It is the same product either way.

What it does today

This is the honest picture of the current product. Built works in the app. Server only works in the API but has no screen yet. Not yet is planned or out of scope.

How it works

OneNGO separates what an NGO wants from the rules that keep money safe.

Six rules nothing can break

  • Every accounting entry balances: debits equal credits.
  • A closed period or year changes only by a reopen with a recorded reason.
  • An issued receipt number is never reused or altered. A void keeps its number.
  • An account balance changes only through a recorded transaction.
  • Permission checks and the audit trail always apply.
  • One organisation's data is never visible to another.

A first month, in seven steps

A picture of how an NGO goes from nothing to taking donations.

  1. OpenAn operator onboards the NGO
  2. Set upThe administrator finishes the checklist
  3. InvitePeople get a link and roles
  4. RecordStaff add donors and donations
  5. ApproveApprovers decide in the Inbox
  6. ReceiptPaid donations get a numbered receipt
  7. AdjustThe administrator changes forms in the Builder

Each step has a how-to in the user guide: the operator onboards, the administrator finishes setup and invites people, users work in Records and the Inbox, and the administrator uses the Builder.

Safe by design

Separate organisationsThe database itself hides one organisation's rows from another. The organisation always comes from who signed in.
Protected moneyRules live in code and in database triggers. Scripts and configuration cannot skip them.
Secrets locked awayPasswords are hashed. Stored credentials and sensitive fields are encrypted. Secrets never sit in files or in the repository.
Everything auditedEvery change has a history. Operator actions are recorded with who, when, and why.
  • Operators sign in with two-step verification, and again before suspending or closing an organisation.
  • The operator console sits behind Google Identity-Aware Proxy in production.
  • Nothing loads from the public internet: no web fonts, scripts, or images from other sites.
  • A security review fixed 16 findings. It is not a substitute for a human penetration test.

Plain words

WordMeaning
OrganisationOne NGO inside OneNGO, with its own people, records, and code (the part after /o/ in its sign-in address).
RecordOne item the NGO keeps, such as a donor or a donation. Its kinds are called record types.
ModuleA ready-made bundle of record types, forms, workflows, and reports. Donations is the one that ships.
DefinitionA saved description of how something looks or behaves. The app reads definitions instead of code.
BuilderThe screen where an administrator drafts, checks, and publishes definitions.
WorkflowThe steps a record moves through, such as Raised then Paid.
ConnectorA saved link to an outside service, such as SMS or a webhook.
Override scriptA small piece of logic for what configuration cannot express. It proposes changes and the platform checks them.
LedgerThe double-entry books. Every entry balances.
OperatorA person who runs the platform itself, not one NGO.
PWAAn installable web app: add it to your phone's home screen and it opens like an app.

About these docs

  • One look. Every page here uses the same stylesheet, assets/docs.css, and the same script, assets/docs.js, on top of the web kit's design tokens. Change a colour or spacing once and every page follows.
  • One document per topic. Extend the existing page. Do not add a second copy in another folder.
  • Plans stay in Markdown. Keep plans in plans/. Never copy them into documents.html, user-guide.html, developer.html, or any other HTML page.
  • Do not rename or move the backend plan (tests read it), the finance plan (migration comments cite it), or the four cited wireframes (the in-app guide cites them).
  • Code paths in Markdown backticks must exist. tests/unit/platform/docs-paths.test.ts checks every `apps/…`, `packages/…`, and `docs/…` path in .md files, except under docs/deleted/ and the historical backend plan.
  • Never put a secret in a document.
  • Retire a document by moving it into docs/deleted/ with the same relative path, then add it to the table at the bottom of this page.

Known gaps

Check the code before relying on these
  • Test plan lists passkey sign-in as unmerged (sections 3.2 and 33). Passkeys are built. Its baseline is the 2026-11-03 commit.
  • The finance plan, work item H1, describes an older migration state.
  • Three wireframes began as proposals (settings screen, theme editor, organisation settings regroup). The app already follows the settings regroup and part of the theme guidance. Confirm against the app before building from the rest.
  • Not yet proven on a live project: Playwright against a live address, the pipeline on a GitHub runner, automatic rollback in practice, and the stage Cloud Run deploy.
