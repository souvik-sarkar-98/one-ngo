# S4 security review — 2026-10-26

Independent review of plan block S4 (records, files, jobs, scripts, configuration, exports, identity and money) before two organisations share one installation.

- **Code reviewed:** branch `review/S4-security-review` at commit `5429fdb`.
- **Reviewer:** an AI agent (see section 5, *Limits*).
- **Probes:** `test/security/s4-*.test.ts`. Each probe asserts the **safe** behaviour. Where the current code is vulnerable the probe is marked `it.fails(...)`, so the suite stays green and the finding can be reproduced. When a fix lands, the probe starts failing ("expected to fail but passed"); at that point, change `it.fails` to `it`.

Run them with:

```text
npx vitest run test/security --maxWorkers=3
```

### Not covered, or only skimmed

- **Dependency vulnerabilities.** There was no internet access and no `npm audit`; `jose`, `otplib`, `quickjs-emscripten`, `fastify` and `pg` versions were not checked against advisories.
- **Cloud configuration.** App Engine/Cloud Run settings, `ops/`, `azure-pipelines.yml`, GCS bucket IAM, Cloud SQL users and roles were not reviewed. The production database role setup is unknown; the test database runs migrations as a superuser.

- **Performance and denial of service** beyond the script sandbox and rate limiting (for example import sizes or query cost).

### Method

1. Built a threat model (section 2).
2. Read each code path end to end, from route to service to store to SQL.
3. Took a live inventory of row-level security, grants and SECURITY DEFINER settings from a freshly migrated test schema.
4. Wrote probe tests against isolated test worlds (`test/helpers.ts`) for every finding that could be shown in-process. Each probe was also run once with `it.fails` switched to `it`, to confirm it fails for the vulnerability and not for a setup error. The failure messages are quoted in the evidence column of section 3.

## 2. Threat model summary

| Actor | Can reach | Main goals considered |
| --- | --- | --- |
| Anonymous internet user | Public routes: sign-in, reset, email code, OIDC, organisation sign-in page and logo, webhooks, `/health`, `/ready`, `/internal/tick` | Account takeover, enumeration, brute force past rate limits, open redirect or phishing, forged webhooks, triggering the scheduler |
| Member of NGO A | Their own records and screens; any delegated permission (payments, people, API keys, script authoring) | Reading masked or sensitive fields, acting beyond their role, financial fraud (marking unpaid donations paid, receipts), escalating to administrator |
| Administrator of NGO A | Everything in NGO A, including connectors, scripts, roles, exports | Reading or affecting NGO B: data, accounts shared with B, availability of the shared instance, platform credentials |
| Script author (`config:script:publish`) | Script code, Try it, effects declared on scripts | Escaping the sandbox, reading data the saver cannot see, effects beyond policy, starving the shared instance |
| Compromised or spoofed payment gateway, or replaying network attacker | `/webhooks/payments/:provider/:tenantKey` | Marking intents paid without money, replay, amount mismatch |
| Operator | Database owner credentials, deploy step, environment | Out of scope as an attacker. Reviewed for blast radius: what any code bug can reach with the owner connection. |

**Trust boundaries.** The organisation boundary is enforced in two layers: application checks, and PostgreSQL row-level security through `app_runtime` with `app.tenant_id`. The process always holds owner credentials (`asSystem`). User accounts (`app_user`) are **global** and shared by every organisation a person belongs to.

### Details

#### S4-1 — Payment request route trusts the caller's amount and paid step (High, blocks pilot)

**Severity:** High. Impact is financial integrity and tax-receipt fraud (80G receipts for money never received), plus bypass of workflow permissions. Likelihood is moderate: it needs only the delegated `payments:create` permission and read access to the record.

**Affected:**

- `src/http/plugins/payments.ts` 59–61: `POST /api/payments`.
- `src/http/contracts/money.ts` 49–84: the client supplies `amount` and `onPaid`.
- `src/domain/payments/payment-service.ts` 118–162: `createIntent` checks only `payments:create` and that the caller can read the record. It does not check that the amount equals the record's amount, or that `onPaid.transition` and `onPaid.fields` come from a published `createPayment` action.
- `src/application/payments/confirm-payment.ts` 22: the paid step runs as `systemActor('payments:…')`.
- `src/kernel/db.ts` 37–39: a system actor has `permissions: ['*']`.

The intended path, a configured action in `engines/actions/action-service.ts` 97–106, takes the amount from the definition's expression and `onPaid` from the definition, which `metadata/cross-refs.ts` 324–329 validates. The raw route bypasses all of that.

**Evidence:** probe `S4-1` in `test/security/s4-money.test.ts`. A collector with only `record:donation:read` and `payments:create` requests ₹1 against a ₹1,00,000 donation. An accounts user confirms the ₹1 that really arrived. Result: `expected { status: 'raised', receipts: [] }`, received `{ status: 'paid', receipts: ['100000.00'] }`.

**Exploit:** A volunteer collects ₹1 by UPI, or pays ₹1 by Razorpay checkout, which confirms automatically by webhook. The donation then shows as paid and a ₹1,00,000 tax receipt is issued. The same route lets them run any transition, and fill any writable field through `onPaid.fields`/`methodValue`, with `*` rights.

**Fix:**

- Remove `POST /api/payments` from the public API, or make it take an action key and derive `amount` and `onPaid` server-side from the published action, exactly as `ActionService` does.
- In `paidStep`/`ConfirmPayment`, run the step as the person who created the intent with the action's authority, not as `*`.
- Refuse confirmation when the paid amount differs from the record's amount field.
- Add an automated test that the record's amount and the intent's amount match.

#### S4-2 — Script sandbox blocks the shared event loop (High, blocks pilot)

**Severity:** High. Impact is cross-organisation availability: the whole instance stops serving. Likelihood is moderate: it needs `config:script:publish` in any one organisation, or simply a buggy script. A loop that hits its limit on every save is an easy mistake.

**Affected:**

- `src/scripts/sandbox.ts` 127–144: `vm.evalCode` runs synchronously on Node's main thread until `shouldInterruptAfterDeadline` fires.
- `schemas/script.schema.json` 19 and `src/engines/builder/builder-support.ts` 464: up to 1000 ms per run.
- Every save runs all enabled before-save, validate, guard and after-save scripts, and nested saves run theirs too.
- `POST /api/builder/scripts/try` (`src/http/plugins/builder.ts` 89) runs arbitrary code on demand. The API rate limit is 300 requests per minute per IP and is spoofable (see S4-4).

**Evidence:** probe `S4-2` in `test/security/s4-scripts.test.ts`. A `setTimeout(0)` queued just before a `while (true) {}` script waited `1002 ms` (the probe expects under 200 ms).

**Exploit:** A script author in NGO A loops calls to Try it with `while(true){}` and `timeoutMs: 1000`. Each call freezes the instance for one second, so NGO B's requests time out and health checks fail. Doing it from a few addresses keeps every instance pegged.

**Fix:**

- Run QuickJS in a `worker_threads` pool, or a separate process, with a hard wall-clock kill.
- Cap total script time per request.
- Add per-organisation concurrency and CPU budgets.
- Put a dedicated low rate limit per user on Try it.

#### S4-3 — Restarting two-step setup switches off the enrolled authenticator (Medium, blocks pilot)

**Severity:** Medium. Impact is a downgrade of sign-in security on a **global** account, across every organisation it belongs to, or lock-out when the attacker confirms their own secret. Likelihood needs a stolen access token or script running in the page.

**Affected:**

- `src/identity/identity-service.ts` 305–311: `beginTwoStep` asks for no password or current code.
- `src/kernel/capabilities.ts` 1203–1213: `startTwoStep` sets `totp_secret_enc = new, totp_enabled = false` on `app_user`.
- Route: `POST /api/auth/two-step/begin` (`src/http/plugins/session.ts` 66).

**Evidence:** probe `S4-3` in `test/security/s4-identity.test.ts`. After enrolment, the password alone is refused. One `beginTwoStep` call with the access token later, the password alone signs in (`Expected error code 'forbidden' but the call succeeded`).

**Exploit:** An attacker who briefly holds a session in NGO A (XSS, shared device, leaked token) calls `begin` and then `confirm` with their own secret. The victim's authenticator stops working for NGO B too: either B's two-step requirement now blocks them, or the attacker owns their second factor. If the attacker also has the password, two-step no longer protects the account.

**Fix:**

- Refuse `begin` while two-step is enabled unless the request carries a fresh password or current code.
- Keep the old secret active until the new one is confirmed (store a pending secret separately).
- Audit and notify the person by email on every change.

#### S4-4 — Rate limits use a spoofable client address (Medium)

**Severity:** Medium. Impact is that all per-IP limits are bypassed: sign-in, reset and code request, organisation-code enumeration, Try it (S4-2), and API traffic. Likelihood is high wherever `GAE_SERVICE` is set.

**Affected:**

- `src/main.ts` 117: `trustProxy: !!process.env.GAE_SERVICE` trusts every hop.
- `src/http/server.ts` 84 and 103–114: Fastify then takes the left-most `X-Forwarded-For` entry, which the client controls, and the limiter keys on `req.ip`.
- `src/kernel/rate-limit.ts` 31–34: once 50,000 keys exist, `sweep` clears every window.
- The DB-backed per-email throttles (`capabilities.ts` 1368–1396) are not affected; the per-IP ones (`identity-service.ts` 478–480) are.

**Evidence:** probe `S4-4` in `test/security/s4-http.test.ts`. With an auth limit of 5, twelve requests from one socket with rotating `X-Forwarded-For` all got `200` (`expected [200, 200, …] to include 429`).

**Fix:**

- Trust exactly the platform's hop count (`trustProxy: 1`, or App Engine's documented hop count), or read the right-most untrusted address.
- Do not clear all windows when the map fills; evict oldest entries instead.
- Consider a shared store for auth limits.

#### S4-5 — Open redirect after provider sign-in (Medium)

**Severity:** Medium. The impact is phishing immediately after a genuine sign-in on the real domain. Likelihood needs OIDC (for example Google) to be enabled.

**Affected:**

- `src/identity/oidc.ts` 53–55: `safeNextPath` accepts `/\t/evil.example`.
- `src/http/plugins/auth.ts` 137: `reply.redirect(result.next)`.

Node accepts a tab in a header value (`http.validateHeaderValue('location', '/\t/x')` passes). Browsers strip tabs and newlines while parsing URLs, so `/\t/evil.example` becomes `//evil.example`. The web app's `safeNext` (`web/src/app/core/shell.ts` 74–76) has the same pattern, but it only navigates inside the router, so it cannot leave the site.

**Evidence:** probe `S4-5`: `new URL(safeNextPath('/\t/evil.example'), 'https://ngo.test/').host` is `'evil.example'`. A control probe shows `//` and `/\` are already refused.

**Exploit:** The attacker sends a link to `/api/auth/oidc/google/start?tenant=asha&next=%2F%09%2Fevil.example`. The victim signs in with Google and lands on a look-alike page asking them to "confirm your password".

**Fix:** Reject any `next` containing control characters or a backslash (`/[\u0000-\u001f\\]/`). Better, parse it with `new URL(next, base)` and require the same origin, then redirect to `pathname + search + hash`.

#### S4-6 — Access tokens survive sign-out (Low)

**Severity:** Low. A 15-minute window after sign-out, password reset or refresh-reuse detection; suspension and role changes are already handled.

**Affected:**

- `src/identity/identity-service.ts` 256–276: `authenticate` checks the signature, membership and `access_version`, but never the token's `sid` (session family).
- `logout` (251–253), `endFamily` and `finishPasswordTokens` (`capabilities.ts` 1329–1340) revoke only refresh tokens.

**Evidence:** probe `S4-6`: after `logout`, `authenticate(accessToken)` still succeeds.

**Fix:** Check that `sid` is a live refresh-token family (cached for a few seconds, like `access_version`), or bump a per-user token version on logout, reset and theft detection.

#### S4-7 — Delegated people and API-key managers can grant administrator (Medium)

**Severity:** Medium. Impact is a full takeover of the organisation (`*`) by anyone holding a narrower delegated permission. Likelihood depends on organisations delegating "Manage people" or "API keys" separately from roles, which the UI encourages.

**Affected:**

- `src/identity/roles-service.ts` 184–207: `setMemberRoles` needs only `members:manage` and works on oneself.
- `src/identity/people-service.ts` 235–267 and 314–338: `add` and `addRoleMembers`.
- `src/identity/identity-service.ts` 324–327: `assign` has no check that the granter holds the role's permissions.
- `src/identity/api-key-service.ts` 68–85: `create` binds a key to any role.

**Evidence:**

- Probe `S4-7a`: a `members:manage`-only member gives themselves `admin`.
- Probe `S4-7b`: an `admin:api-keys`-only actor creates a key for `admin`.

Both succeed.

**Fix:** Refuse to assign a role, or bind a key to a role, whose permissions are not a subset of the actor's own, unless the actor holds `admin:roles`. Forbid changing one's own roles.

#### S4-8 — Try it bypasses the script-admin gate for inputs (Low)

**Severity:** Low. Impact is that finance totals become readable by script authors. It stays inside one organisation, and authors are semi-trusted.

**Affected:**

- `src/engines/builder/builder-support.ts` 452–526: copies `inputs`, `effects` and `runAs` from the request (486) without `adminOnlyParts`/`config:script:admin`.
- `src/engines/records/record-service.ts` 640–642: loads `balances` with no permission check.

Publishing is gated (`metadata/definition-service.ts` 80–84). Try it is not.

**Evidence:** probe `S4-8`: an author without `config:script:admin` receives `inputs.balances` from Try it.

**Fix:** Apply `assertScriptPublisher`, or the same `adminOnlyParts` check, in `tryScript`. Require a money permission to load balances outside a published admin script.

#### S4-9 — Erasure leaves personal data behind (Medium)

**Severity:** Medium. The impact is DPDP non-compliance: an erased person's values remain in readable tables and in exports. The weakness is certain to apply; whether it is exploitable depends on who reads those tables.

**Affected:** `src/application/privacy/privacy-service.ts` 170–230 and `infrastructure/postgres/stores/privacy-store.ts`. Erasure touches `record`, `file_object`, `notification` and record audit entries only.

Not touched:

- `idempotency_key.response`: full response bodies (`kernel/idempotency.ts` 98–107), kept for 24 hours.
- `outbox_event.payload`: `action.notify` values, `script.notify` masked record, webhook bodies.
- `job_item.data`: import rows.
- `record_import`: the uploaded CSV, until cleanup.
- `approval_request.data`: proposed changes.
- `payment_event.payload`: the gateway webhook body, which carries the payer's email or phone.
- `connector_delivery.error`.
- `script_run.message`.
- Non-record audit entries, such as `file.uploaded` names.
- Application logs: database error messages include constraint details (`http/errors.ts` 44–52).

Most of these tables are also in the whole-organisation export (`kernel/tenant-export.ts`).

**Evidence:** code inspection only; no probe was written.

**Fix:** Extend erasure, or a scheduled scrub, to these tables by record id and subject. Shorten idempotency and outbox retention. Document what is kept and why for counsel.

#### S4-10 — Cross-organisation account disclosure when adding members (Low)

**Severity:** Low. The impact is a cross-organisation leak of a person's existence, display name and disabled status, plus membership without consent.

**Affected:** `src/identity/people-service.ts` 256–264. It adopts the existing account's `display_name` and returns distinct conflict messages ("…is switched off…"). `accounts.add` in `capabilities.ts` 1159–1168 joins the existing global account.

**Evidence:** probe `S4-10`: NGO A adds an email that exists in NGO B and reads back `'Bodhi Secret Name'`.

**Fix:** Keep the organisation-local name typed by the adder, with a per-organisation display name on the profile. Use uniform messages. Consider an acceptance step before an existing account joins another organisation.

#### S4-11 — Two-step code replay (Low)

**Affected:** `src/kernel/crypto.ts` 263–270. It accepts ±1 period and stores no last-used time step.

**Evidence:** probe `S4-11`: the same code signs in twice.

**Fix:** Store the last accepted time step per user and refuse codes at or before it.

#### S4-12 — Jobs keep the creator's old rights (Low)

**Affected:** `src/kernel/jobs.ts` 192 stores the actor JSON at creation, and 386 runs batches with it. An export started by someone who is then suspended, or whose role is removed, keeps exporting.

**Fix:** Re-resolve the actor through the member store at each batch, and cancel jobs of suspended or removed members.

#### S4-13 — Global lockout by email (Low)

**Affected:** `src/identity/identity-service.ts` 478–496 and `capabilities.ts` 1379–1396. The `email:<address>` throttle is shared by all organisations: five wrong passwords lock the person out of every organisation for 15 minutes, and anyone can repeat this.

**Fix:** Use progressive delays instead of hard lockout, key the lock on email + IP, or offer an email-code bypass.

#### S4-14 — Row-level security does not stop SQL injection (Informational)

**Affected:**

- `src/kernel/db.ts` 94–97 and `pg-database.ts` 97–104: tenant transactions start as the owner login and only `SET LOCAL ROLE app_runtime`.
- Any multi-statement injection can `RESET ROLE`.
- Even single-expression injection can call `set_config('app.tenant_id', '<other org>', true)`, because `app_runtime` may set custom settings.

No injection was found, but row-level security here only protects against application logic bugs, not injection.

**Fix (defence in depth):**

- Connect the serving pool as a dedicated login role that is a member of `app_runtime` but is not the owner; keep owner credentials for deploy and a narrow system pool.
- Bind the tenant to something `app_runtime` cannot change, for example a session-start `SECURITY DEFINER` setter that refuses a second change in the transaction.
- Add a start-up check that the serving role lacks `BYPASSRLS` and ownership.

#### S4-15 — Connectors can reach internal https services (Informational)

**Affected:** `src/engines/connectors/connector-service.ts` 109–116 (https-only, no address filter) and 422 (a non-2xx body excerpt is stored and shown to administrators). Redirects are not followed and the cloud metadata server is plain http, so platform credentials are not reachable this way.

**Fix:** Resolve and refuse private, loopback and link-local addresses at connect time.

#### S4-16 — Webhook hardening (Informational)

**Affected:**

- `src/domain/payments/providers.ts` 74: the Razorpay event id comes from the unsigned `x-razorpay-event-id` header, so a captured body can be replayed under a new id. This is harmless today because intents must be `awaiting_payment`.
- `payment-service.ts` 212: the amount check is skipped when the provider omits an amount.
- Neither provider checks timestamp freshness.

**Fix:**

- Derive the event id from the signed body.
- Treat a missing amount as a mismatch.
- Refuse Cashfree events with stale `x-webhook-timestamp`.

#### S4-17 — Enumeration and logout CSRF (Informational)

**Affected:**

- `src/http/plugins/organisation.ts` 29–32: a 200 or 404 per code reveals which organisation codes exist. This is by design for the sign-in link, and limited only by the per-IP limit (see S4-4).
- `src/http/plugins/auth.ts` 39–48: with `CORS_ORIGINS` set, the refresh cookie is `SameSite=None`, so any site can POST `/api/auth/logout` and sign the person out.

**Fix:** Accept the enumeration or use unguessable sign-in links. Require an `Origin` in the allow-list for logout and refresh.

## 4. Verified as safe

Evidence for each point is a probe (P), an existing test (T) or code inspection (C).

**Tenant isolation**

- **Row-level security inventory.** Every table the runtime role can touch has RLS with `tenant_id = app_tenant()`. The auth tables without RLS (`refresh_token`, `password_token`, `email_code`, `oidc_login`, `user_identity`, `auth_throttle`, `rate_limit`) have no runtime grants at all. `app_user` exposes only id, name, email and status to members of the current organisation. (P: `RLS inventory` tests in `s4-http.test.ts`; T: `tenancy.test.ts`.)
- **Runtime role privileges.** `app_runtime` is not superuser and lacks `BYPASSRLS`. Every SECURITY DEFINER function pins `search_path`, and the record query functions add `pg_temp` last (migration 016, lines 115–124). (P.)
- **Tenant id handling.** The tenant id is UUID-checked before the preamble, and `set_config` is parameter-bound. (C: `pg-database.ts` 97–104; T.)
- **Owner-level paths.** Every query in `kernel/capabilities.ts` and `tenant-export.ts` reviewed filters by an explicit tenant id or key. The export nulls `connector.secret_enc` and `api_key.secret_hash` and omits password and two-step columns. (C.)
- **Erasure functions.** `app_erase_audit_values` and `app_erase_account` refuse without `app_tenant()`, touch only the current organisation's rows, erase only suspended members, and leave accounts shared with other organisations unchanged. (C: migration 020; T: `erasure.test.ts`.)

**Injection**

- **Record queries.** Values travel only as `$1` jsonb elements. Keys go through `sqlKey`. Filters, sorts and totals on sensitive or unreadable fields are refused. Search text excludes read-protected fields. `app_record_clause_ok` re-checks the compiler's grammar inside the database. (C; T: `dynamic-sql-hostile.test.ts`, `record-query.test.ts`.)
- **Expression language.** No method calls, and `__proto__`, `prototype` and `constructor` are blocked; only own properties of plain objects are read. (C: `expressions/expression.ts` 38, 238, 295.)

**Scripts**

- **Sandbox.** QuickJS in WASM gets only a JSON copy of its input. Memory, stack, time and 256 KB input/output caps apply. Effects are data checked by an Ajv schema, then per-type policy: declared types, accounts, connectors, named recipients, balanced journals, `maxTotalAmount`, effect budgets, no self-update. Then the owning engine checks them again. (C; T: `sandbox.test.ts`, `script-effects*.test.ts`.)
- **Publish rules.** Publishing or rolling back a `runAs` or `balances` script needs `config:script:admin`. (C: `definition-service.ts` 80–84.)

**Money**

- **Ledger and receipts.** Journals must balance, closed periods are refused, and posted journals and issued receipts are immutable through triggers. (C: migration 001, 192–313.)
- **Webhooks.** HMAC is computed over the raw body bytes with a constant-time compare, using each organisation's own credentials. A Razorpay webhook secret is required. Events are idempotent per event id, and amount mismatches are audited, not paid. (C; T: `money-payments.test.ts`.)

**Secrets and sign-in**

- **Secrets at rest.** Gateway, connector and OIDC secrets and two-step secrets use AES-256-GCM with a key ring. Sensitive record fields use HKDF-derived keys with context-bound authenticated data and blind-index HMAC. Secrets never reach responses: the response schemas allow none (`gatewayListResponse`, `connectorResponse`). (C; T: `response-secrets.test.ts`, `field-encryption.test.ts`.)
- **Credentials and tokens.** Passwords use scrypt, with timing equalised for unknown accounts. Reset, invite, email-code, ticket and refresh tokens are stored as SHA-256 hashes with attempt caps. Refresh tokens rotate, and reuse revokes the whole family. JWTs pin HS256, require `exp`, check `typ`, and need a secret of at least 32 characters. (C; T: `identity.test.ts`, `auth-flows.test.ts`.)
- **Browser token handling.** The refresh cookie is `HttpOnly; Secure; SameSite=Strict; Path=/api/auth`. The web app keeps the access token in memory only; `localStorage` holds only the last organisation code and UI preferences. (C.)
- **Public sign-in routes.** Reset, email code and the organisation page answer uniformly, with DB-backed per-address and per-IP limits on sending. (C; T.)

**HTTP surface**

- **Route guard.** Every route outside the documented public list answers 401 or 403 without credentials, and the list is read from Fastify's router. Header sign-in (`devAuth`) is refused outside `NODE_ENV=test` and on cloud hosts. (T: `route-guard.test.ts`; C: `server.ts` 49–54.)
- **Operations endpoints.** `/internal/tick` takes either a constant-time bearer on POST only, or the App Engine cron header only when `GAE_SERVICE` is set. `/ready` and `/health` reveal nothing. 500 responses carry only a request id. (C; T.)
- **Headers.** The CSP is `script-src 'self'; object-src 'none'; frame-ancestors 'none'`, together with `nosniff`, HSTS, `no-store` on `/api/`, and an explicit CORS allow-list where `*` is refused. (C.)

**Files**

- **Uploads and downloads.** File type is sniffed from content; markup-like text and macro Office files are refused. Size and quota are enforced while streaming. Storage keys are `<tenant>/<uuid>`, never user paths. Names are cleaned. Only images and PDF open inline. Linked files need read access to the field; unlinked files are visible only to the uploader. Logos are served under RLS. (C; T: `files.test.ts`.)

**Exports, rich text and connectors**

- **CSV.** Formula prefixes are escaped, and export uses the list's visibility and masking. (C: `csv.ts` 63–74.)
- **Rich text.** The server-side allow-list sanitiser is followed by a client-side DOM prune. The template preview renders escaped text in a sandboxed iframe with its own CSP. (C.)
- **Connectors.** Only https, no redirects followed, CR/LF refused in headers, and custom connector kinds cannot impersonate OIDC providers. Organisation-run OIDC providers have no HTTP route today. (C.)

## 5. Residual risks and limits of this review

- **AI review, same tool family.** This review was done by an AI agent from the same tool family that built the code. It may share the builders' blind spots and is **not a substitute for a human penetration test**, especially of authentication flows, the deployed cloud configuration and the browser app.
- **Static reading plus targeted probes.** No fuzzing of the query grammar guard, the sanitiser or the CSV parser. No load testing beyond the event-loop probe.
- **Production database roles unknown.** If the serving connection is a superuser or has `BYPASSRLS` in some host setup, `SET LOCAL ROLE` still drops privileges, but S4-14's injection escape becomes more serious. A start-up assertion is recommended.
- **Dependencies not audited.** No advisory database was available.
- **Provider behaviour assumed.** Razorpay and Cashfree signature schemes, Google OIDC claims and App Engine header stripping (`X-Appengine-Cron`) were assumed to behave as the code's comments state.
- **Cross-organisation design choices accepted as given.** Global accounts and a shared Node process mean an availability or account-security issue in one organisation can affect another (see S4-2, S4-3, S4-10, S4-13). The pilot should be monitored per organisation for script time, error rates and sign-in failures.
- **Earlier claims still unverified.** Architecture docs were treated as claims; where this report says "safe" it is backed by the evidence column above, nothing else.

### Top recommendations

1. **Close S4-1.** Derive payment amount and paid step from published actions, never run the step as `*`, and refuse amount mismatches on confirmation.
2. **Move script execution off the main thread (S4-2)**, with per-organisation time budgets and a strict limit on Try it. Fix the proxy trust (S4-4) at the same time, since it widens S4-2.
3. **Harden the shared account (S4-3, S4-6, S4-7, S4-11).**
   - Require re-authentication to restart two-step, and keep the old secret until confirmation.
   - Tie access tokens to their session.
   - Stop delegated roles from granting more than they hold.
   - Make two-step codes single-use.
