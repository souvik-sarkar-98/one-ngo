Legacy data migrator proposed

These screens show the changes in docs/plans/legacy-data-migrator-plan.md. The six steps of /admin/migration (Files, Map, Order, Books, Check, Run) stay as they are. What is new: a People file kind, legacy user id columns for person fields, attachments for file fields, a Check with warnings, and Delete source data after a run. Asha is an administrator holding data:migrate, data:migrate:people and members:manage.

People arrive InvitedNo password, no two-step secret and no email is created. Each person sets a password later from an invitation, a reset link or an emailed sign-in code.
Legacy ids stay internalA per-organisation table maps each legacy user id to the new person. Records can then fill person fields from the legacy id, whether it is a UUID, a number or text.
Check says everything firstBlocking problems and warnings are listed before anything is written, including unresolved people and files. It never says anything about accounts other organisations hold.
Re-runs update, never duplicateThe same profile run twice changes nothing the second time except edits. Status and roles added by hand are never undone.
