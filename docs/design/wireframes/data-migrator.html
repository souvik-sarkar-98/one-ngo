Data migrator

Asha brings the old system’s tables into this organisation from CSV files. Any file is accepted: any name, any columns, any number of files. Each file keeps the header row it arrived with. She maps those columns onto a record type that already exists in the Builder, then runs the whole set in order. The screen lives in the core app at /admin/migration. The operator console does not load records.

Any CSVThere is no template and no required header. A donors file, a volunteers file and a ward-visits file can sit in one profile even when none of their columns match. A column she does not need stays on Not imported.
Map, then loadShe chooses the record types each file fills (one row can make a supporter and their donation), which column is the old id, and which column fills each field. A donation’s donor column looks up the donor loaded earlier by that old id. The map is saved with the profile and reused on the next run.
The type comes firstThe file does not create a record type or a field. If nothing in the Builder can hold the table, she leaves that file out and adds the type in the Builder, then comes back. Calculated fields, rollups, files and signatures are not in the field list.
Books stay separateOpening balances and the next receipt number are entered on Books. Old transfer tables are not loaded as journals. Automations stay off for the run.
