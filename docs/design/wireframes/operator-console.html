Operator console — complete wireframe

Ravi runs the hosted platform. He signs in to the console with two-factor authentication, looks up organisations, onboards new ones, changes an organisation's state and sign-in, gives colleagues access, and reads what everyone did. Every one of these is a screen. Nothing in the console needs a command line. The only step outside it is creating the very first operator on a new installation, which the database administrator does once with SQL.

This page covers every screen and every state the console can be in: the happy path, empty and loading states, refusals, errors, and what each operator sees depending on the actions they hold. Screens tagged state are variants of the screen above them. Screens tagged proposed go beyond what the console server does today and need server work.

Same frame as the main appApp bar with the product name and the operator's initials, one breadcrumb line, the rail on a wide screen and the bottom bar on a phone, and one centred content column. The same tokens, cards, panels, fields, sheets and badges as the main app. The app bar's second slot reads Operator console. Sign out is the last rail icon on a wide screen; on a phone the initials open a sheet with Sign out.
Destinations follow grantsOrganisations, Onboard, Operators and Activity. A destination appears only when the operator holds an action it needs (see the table below). Buttons on a page follow the same rule. An address the operator cannot use shows a no-access page, never a broken screen.
Fresh two-factor checkSuspend, reactivate, close, changing an organisation's sign-in, and every change on Operators send the operator through a fresh two-factor sign-in first. The change is made only when they return, the check names exactly what it allows, and it can be used once within five minutes.
No command linegrant.ts and npm run grant are removed. Adding operators, giving and removing actions, changing a login and disabling an operator are all on Operators, and each change is written to platform_audit. Onboarding is a form, not JSON.
First operatorA new installation has no one who could sign in to add the first operator. The database administrator inserts that one operator, with Manage operators, using SQL (utilities/seed/console-operator.sql locally). Everyone after that is added on Operators.
No lock-outAn operator cannot disable themselves, change their own login, or remove their own Manage operators. Anyone on Operators holds Manage operators, so the console always keeps at least one operator who can add others. The server enforces the same rules; the screens show them before anyone tries.
Lookup, not a directoryThe console still does not list every organisation. Organisations is a lookup by code or request ID. The only lists are recent lookups in this browser, operators, and activity.
Plain words, no JSONEvery response is drawn as fields, badges, checklists and history. Errors are sentences placed on the field or at the top of the page. Raw JSON is never shown, including at /op/auth/callback.
