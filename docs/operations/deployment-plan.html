Production deployment plan and CI/CD test gates

NGO platform on Google App Engine standard (Mumbai), deployed by GitHub Actions from master. Stage on Cloud Run is phase 2.

1. Decisions

QuestionDecisionWhy
Where does production run?App Engine standard, F1 instances, asia-south1 (Mumbai). Two services: default (organisation app) and console (operator console).The F1 free allowance covers a small NGO workload. The app is a plain Node server, so no container build is needed.

Where does the pipeline live?GitHub Actions, in this repository.No separate deploy project to keep in step. Azure Pipelines is not used.
Which branch deploys?master only. develop runs the tests and deploys nothing.Stage does not exist yet.
How do credentials reach Google Cloud?Workload identity federation, limited to this repository and refs/heads/master. No service-account key file.Nothing long-lived to leak or rotate.
How do secrets reach the app?GitHub environment secrets, written into app.yaml on the runner at deploy time. Never committed.App Engine standard cannot read Secret Manager values into environment variables by itself. See the trade-off in section 7.
How is a release made safe?Deploy with no traffic, smoke-test, move traffic, smoke-test the public address, move traffic back on failure.App Engine keeps old versions, so going back is a traffic change, not a rebuild.

2. Production topology

Staff and members use https://<project>.<region>.r.appspot.com. The console is on https://console-dot-<project>.<region>.r.appspot.com. Read the exact host from gcloud app describe --format="value(defaultHostname)" after creating the app. A custom domain can come later; if you add one, change PUBLIC_BASE_URL and the redirect addresses registered with Google sign-in and each connector.

One database, four logins. The same PostgreSQL database holds everything. Five connection strings point at it with different logins: DATABASE_OWNER_URL (migrations, used only by the deploy job), then DATABASE_SYSTEM_URL, DATABASE_RUNTIME_URL (main), OPERATOR_DATABASE_URL, OPERATOR_RUNTIME_URL (console). Pointing two of them at the same login defeats the separation the server relies on.

4. The pipeline

Three workflows in .github/workflows/. Colour: green is an automated gate, amber needs a person, red is where a failure stops everything after it.

On a pull request, and on any push to develop

Open or update pull request
Typecheck, build, testPostgres service, npm run ci
Dependency auditnpm run ci:audit
CI gateNeeds both jobs green. The one required check.
MergeBlocked while CI gate is red

On a push to master (or a manual run of CI on master)

1. CI gateSame two jobs again, on the merge commit
2. ApprovalRequired reviewer on environment prod
3. BuildBoth servers from this exact commit
4. Fill manifestsMissing secret stops here, before anything changes
5. Migratedeploy:prepare with the owner login
6. Deploy, no trafficBoth services, --no-promote
7. Curl /healthBoth new versions, before any user sees them
8. Move traffic100% to the new versions
9. Curl /healthPublic addresses. Failure moves traffic back.
10. CronDeploy cron.yaml. Old versions stay for rollback.
11. PlaywrightSeparate job. Opens both sign-in pages. Does not write data.

Why the build is repeated instead of passed from CI

CI already has a test (apps/onengo/server/test/artifact.test.ts) that builds the bundle twice from clean and fails if the two results differ. So building again from the same commit in the deploy job gives the same bytes CI tested, without moving artifacts between jobs.

Why the database moves before the code

The server refuses to start if deploy:prepare has not run (tested in the same artifact test). So the order is fixed: migrate, then start new code. The old version keeps serving against the new schema for the minutes between steps 5 and 8.

Rule for every migration: it must work with the previous release too. App Engine rollback moves traffic back but cannot undo a migration. Drop or rename a column only in a later release than the one that stopped using it.

6. Health curl, then Playwright

Inside the deploy job, .github/scripts/smoke-test.mjs does one thing. It waits up to two minutes, because a new App Engine version starts on its first request, then sends GET /health and requires 200 and {"status":"ok"}. It does this for the main service and the console, first on the new versions and again on the public addresses. The console serves that route from buildOperatorServer. A failure before traffic moves stops the release. A failure after traffic moves sends traffic back.

After that job succeeds, the Post-deploy end-to-end job installs Playwright in tests/e2e and runs two browser checks against the public addresses:

  • The app's /sign-in page shows the organisation-code field.
  • The console home redirects to its sign-in page and shows Console sign in.

That job does not receive the production database secrets and it does not sign in. If it fails, the workflow is red, the Playwright report is kept for seven days, and the new version keeps serving. Go back with the rollback workflow.

7. Rollback and its limits

Automatic

The deploy job records the version serving each service. If the public GET /health fails, or the traffic move itself fails part-way, the job sets both services back to the recorded versions and the run ends red. The Playwright job runs only after this job has succeeded, so a browser failure does not move traffic.

Manual

Run workflow Rollback (production) from master with a version name from a deploy summary, for example g1a2b3c4d5-r12. It checks the version exists on both services before moving either, then curls GET /health on both public addresses. It needs approval from the same prod reviewers. It does not re-run Playwright.

CaseBehaviour
First ever deploy of a serviceThere is no earlier version. The run prints a warning instead of rolling back. App Engine sends the first version all traffic.
Migration already appliedNot undone. Rolling back is safe only if the migration works with the older release (see section 4).
Version already cleaned upRollback only reaches versions the cleanup workflow has not deleted. By default that is the newest five per service, plus any version still taking traffic. The rollback workflow says so if the version is missing.
Same commit deployed againGets a new version name from the run number, so it can never overwrite the version serving traffic.
Two deploys at onceThe deploy-prod concurrency group queues the second.
Secrets live in the version. App Engine stores the filled app.yaml values with each version, and anyone with App Engine viewer access on the project can read them in the console. Keep project membership to the few people who may see production credentials. Moving to Secret Manager means reading it in application code at start-up, which is a code change and not part of this pipeline.

8. Cleanup

Taken from the deploy repository's ops-gcp-cleanup workflow and reduced to this one production project. The release workflow does not delete anything. Cleanup is its own workflow, .github/workflows/cleanup.yml.

WhatRule
App Engine versionsPer service, keep every version that has traffic, and keep the newest five whether or not they have traffic. Delete the rest. If the traffic split cannot be read, the version is kept. The deploy repository keeps two; five matches the rollback window in section 7.
Staging bucketstaging.<project>.appspot.com. Files older than three days. App Engine uploads the source here on every deploy.
Artifact RegistryUntagged images in every repository in the project. A standard App Engine Node deploy may leave none; the step reports that and moves on.

Monday, Wednesday and Friday at 17:00 UTC the workflow runs as a dry run: the report lists what it would delete, and it deletes nothing. To delete, open Actions → Cleanup (production) → Run workflow and untick dry run. Both kinds of run use the prod environment, so a reviewer approves before any Google Cloud call. The run uploads cleanup-summary.md and writes the counts into the job summary. A dry run's deleted count is zero; the report is the list.

The schedule only fires once this file is on the repository's default branch. The first useful run is a dry run, so a missing permission shows up as a warning before anything is removed.

10. Database set-up (once, before the first pipeline run)

The first pipeline run cannot pass its smoke tests until the four serving logins exist, and the logins can only be granted group roles that the first deploy:prepare creates. So do this once by hand.

  1. Create the database at your provider (PostgreSQL 15 or later, with the pg_trgm extension available). Note the owner connection string.
  2. From a checkout, run the migrations with the owner login: 
    npm ci
npm run build:server
$env:DATABASE_OWNER_URL = "postgres://owner:...@host/db?sslmode=require"
npm run deploy:prepare
  3. As the owner, create the four logins (generate a different long random password for each) and grant each its group role: 
    create role ngo_main_system_login     login password '<generated>';
grant ngo_main_system     to ngo_main_system_login;

create role ngo_main_runtime_login    login password '<generated>';
grant ngo_main_runtime    to ngo_main_runtime_login;

create role ngo_operator_login        login password '<generated>';
grant ngo_operator        to ngo_operator_login;

create role ngo_operator_runtime_login login password '<generated>';
grant ngo_operator_runtime to ngo_operator_runtime_login;
  4. Build the four connection strings with these logins and store them as the four database secrets. Add ?sslmode=require if your provider requires encrypted connections.
  5. Open gap: create the first console account (a row in operator_account, migration 030, linked to the identity provider's subject). The repository does not yet document a production procedure for this. Ask the development team for it before go-live, or nobody can sign in to the console.
The role statements follow the bundle test in apps/onengo/server/test/artifact.test.ts, which creates the same logins the same way and starts the real bundle with them. The local development script creates its runtime login with noinherit; the hosted pattern above is the one the bundle test proves.

Free managed databases pause or limit idle projects, cap storage, and differ in backup retention. Check yours against the backup and restore drill (O4) in docs/operations/devops-handover.md before the first real member is added.

14. Stage on Cloud Run

.github/workflows/cd-stage.yml runs after CI gate passes on develop. Production's workflow is not involved. Use a separate Google Cloud project so stage does not consume the App Engine free hours. The free Cloud Run allowance (180,000 vCPU-seconds, 360,000 GiB-seconds, 2 million requests a month, per billing account) applies in Mumbai.

  • Services: ngo and ngo-console in asia-south1, or GCP_REGION. Minimum instances 0, maximum 1, 512 MiB, one CPU, CPU only while a request is in progress.
  • Image: .github/scripts/stage-cloud-run.mjs writes a Dockerfile next to the built dist. Cloud Build runs it. No secret is in the image.
  • Secrets: the stage environment holds the same names as production, plus TICK_SECRET. .github/scripts/sync-stage-secrets.sh copies them into Secret Manager and grants each runtime service account its own secrets. Cloud Run mounts them with --set-secrets.
  • Database: its own database and four logins, never production's. The workflow runs deploy:prepare with the stage owner login. Seed it from utilities/seed/ when you want sample data.
  • Release: the new revision is tagged candidate and gets no traffic until GET /health answers. Traffic then moves. A failed public check returns traffic to the previous revision. rollback-stage.yml does the same later, from develop, given the two revision names.
  • Scheduler: Cloud Scheduler posts /internal/tick every hour with Authorization: Bearer TICK_SECRET. The token is visible to anyone who can read the job.
  • First address: leave PUBLIC_BASE_URL and CONSOLE_PUBLIC_BASE_URL empty for the first run. The health check uses the Cloud Run URLs. The revision itself still has https://pending.invalid until you copy the URLs from the deploy summary into those variables and run again. Do that before anyone signs in.
  • Identity: the stage workload identity trusts refs/heads/develop only. The production pool stays limited to master. The deploy account needs Cloud Run, Cloud Build, Secret Manager, and Cloud Scheduler access, and permission to act as both runtime service accounts. Treat that as a starting set and tighten it after the first run.

15. Go-live checklist

  1. Merge the branch that adds these files into develop, then develop into master once the gate is green on a pull request.
  2. Create the Google Cloud project, App Engine app, service accounts and workload identity (section 11).
  3. Create the database, run the first deploy:prepare, create the four logins (section 10).
  4. Create environment prod and add the variables and secrets (sections 8, 11).
  5. Protect master and develop with the CI gate check.
  6. Register the public addresses with the identity provider (console redirect /op/auth/callback) and, if used, Google sign-in (/api/auth/oidc/callback) and connectors (/api/connectors/oauth/callback).
  7. Push to master. Approve. Read the deploy summary. Write down the release name.
  8. Rehearse a failed release and a manual rollback once, before real data is in.
  9. Run Cleanup (production) once as a dry run and read the report. Delete only after that report looks right.
  10. Complete the alerts (O3) and the backup and restore drill (O4) in docs/operations/devops-handover.md.
  11. Get the first console account created (section 10, open gap).
