The big picture

OneNGO is one codebase that builds two servers and three web apps. They share one set of packages and one PostgreSQL database. An NGO's features (donations, members, expenses) are definitions, which is data. One generic runtime reads them. Money rules, sign-in, and tenancy are fixed code that no configuration can bypass.

Configuration, not codeRecord types, forms, workflows and reports are definitions. Admins publish them in the Builder. No release is needed.
Fixed money rulesBalanced journals, gap-free receipts, closed years. They are code and database triggers. Scripts and config cannot skip them.
Small to runOne Node process, no cache or queue. It scales to zero and fits a 384 MB App Engine F1 instance.

Where PostgreSQL comes from

npm run dev:setup and npm run dev start a local PostgreSQL for you when nothing is listening on the DATABASE_URL port and the install is found. They look at PG_BIN (the folder with pg_ctl) and PGDATA, defaulting to %LOCALAPPDATA%\postgres\pgsql\bin and %LOCALAPPDATA%\postgres\data. They only ever start a database on localhost, and they never stop it. If you run PostgreSQL another way, just start it first.

Step 1: Get the code and install

git clone <your repository address> one-console
cd one-console
npm ci

One npm ci at the repository root installs every app and package, because they are npm workspaces with a single lockfile.

Step 2: Create your .env

Copy the template, then fill the two secrets. .env is ignored by git. The server never reads .env in production, only on your machine.

copy .env.example .env

openssl rand -base64 32     # paste as ENCRYPTION_KEY (32 random bytes)

Using the operator console too?

Also set OPERATOR_ENCRYPTION_KEY and OPERATOR_INTERNAL_TOKEN_SECRET to values that differ from the main ones, and point OPERATOR_OIDC_* at the sandbox. The values are in the sandbox page.

Step 3: Prepare the database

npm run dev:setup

Run it once, and again after you pull new migrations. It creates the database if missing, applies the migrations, creates the non-superuser runtime logins, and loads the demo organisations. A runtime login that is the postgres superuser is refused at start-up, because a superuser would bypass row-level security.

To load only some organisations, add --org for each: npm run dev:setup -- --org demo --org harbour.

Step 4: Start everything

npm run dev

One command starts the sandbox, the main server, the organisation app, the guide, and the operator console. Ctrl+C stops them. If one app exits, the rest stop. PostgreSQL keeps running.

Code layout

The engine, packages/platform, has five layers. Each layer may only call the one beside it on the right, plus the ports it owns. Tests hold these rules, so a wrong import fails the build.

Who may import whom
RuleWhy
@onengo/kernel imports no other @onengo/* package.The kernel (ports, errors, crypto, logging, environment) has no idea what an NGO is.
@onengo/platform imports only the kernel.The engine stays free of any app.
No app imports another app.Apps share code only through packages.
The main server imports platform/main, /contracts, /deployment, never /operator.A tenant-facing process must not hold control-plane code.
The console server imports platform/operator and /contracts, never /main.The console must not be able to act as a tenant.
Web apps import platform/browser and /contracts, never a server app.Request and response types are shared; server code is not.

Change wording or add a languageThe language packs in packages/product/locale.
Call a new outside serviceA port in the kernel or domain, an adapter in infrastructure, and a fake in apps/service-sandbox.

How it works

One request, start to finish

BrowserCalls /api/… with a session token.
Route pluginChecks the token and validates the body against the shared contract.
Use caseApplication layer. Starts one transaction.
EnginesRuntime and domain rules decide. Scripts may propose changes.
PostgreSQLThe tenant is bound; row-level security limits every row.

Every request for one organisation runs inside withTenant(). It switches the connection to the app_runtime role and sets app.tenant_id for that transaction only. Row-level security then hides every other organisation's rows. The organisation always comes from the signed-in identity, never from a request parameter.

Definitions become behaviour

AuthorIn the Builder, or as plain JSON files written in Cursor.
DraftNothing changes for users yet.
CheckJSON Schema and cross-reference rules, as a set.
PublishA new version. Older versions stay restorable.
RunThe generic engines read the published version.

Publishing never changes historical records. A shipped module keeps the organisation's own edits as a patch, so product updates still arrive. The deploy step re-applies each organisation's patch onto a changed platform definition and logs a warning for any that no longer fit.

Saving a record

  • One transaction per command. The save stages live under packages/platform/src/runtime/records/save/.
  • An override script only proposes changes. The platform checks them and applies them in the same save, or not at all.
  • Limits: 20 proposals per run, 50 per save, five levels of nested saves.
  • A script cannot issue or change receipts, reverse entries, open or close a year, or delete records. Journals must balance, use declared accounts, and fall in an open year.
  • Triggers in the database repeat the key money rules, so even a bug in code cannot unbalance the ledger.

Background work

Who calls the tickHow
App Engine (production)GET /internal/tick, accepted only with the X-Appengine-Cron header. Configured in cron.yaml.
Cloud Scheduler (stage, or anywhere else)POST /internal/tick with Authorization: Bearer <TICK_SECRET>. The bearer is never accepted over GET.

One NGO or many

one-ngo (default)One organisation per installation, in its own Google Cloud project and database. Tick every 60 minutes. Scales to zero.
sharedMany organisations on one installation. Set INSTALLATION_MODE=shared. The organisation comes from the signed-in identity. Tick every 5 minutes, and at least one instance stays warm.

The two modes differ only in how the organisation is found and in the operator tooling. Row-level security runs in both, so every one-ngo deployment also tests the shared mode.

Health and shutdown

  • GET /health answers {"status":"ok"} and touches nothing.
  • GET /ready runs select 1 with a 2-second limit and answers 200 ready or 503 unavailable. This proves the database answers.
  • On shutdown the server stops accepting connections, finishes requests it already has, lets the outbox batch finish (at most 10 seconds), closes the pool, and exits 0.
  • Role changes reach every instance within 5 seconds. The database bumps tenant.access_version, and each instance compares it after 5 seconds.

Database and tenancy

One PostgreSQL 15+ database. Five logins with different powers, so a mistake in one process cannot do the work of another. No serving login owns tables, has BYPASSRLS, or is a member of the owner.

LoginUsed byMay do

ngo_main_runtime (member of app_runtime)Main serverTenant traffic under row-level security.
ngo_main_systemMain serverListed security-definer functions only: sign-in lookup across tenants, outbox dispatch, jobs, tick, retention.
ngo_operatorConsole serverOnboarding, lifecycle, platform audit, operator tables.
ngo_operator_runtime (member of app_runtime)Console serverThe tenant steps that onboarding runs.

Migration rules

  • There are 7 files, 001_core.sql to 007_bank_reconciliation.sql, in packages/platform/migrations/. A file's name is its history row.
  • Before the first release, keep the files in final-state form: change the file that owns the table instead of adding a patch file. A database made under older files must be dropped and recreated. From the first release on, do not rename, renumber, or edit an applied file. New changes go in a new file after the last one.
  • A migration may change schema. It may not write data except its own bookkeeping row (the CI check check-migrations.mjs enforces this). Back-fills and seed rows belong in a script you run on purpose.
  • Add before use, drop later. Moving traffic back cannot undo a migration, so every migration must work with the release before it. Drop or rename a column only in a release after the one that stopped using it.
  • Only the deploy step migrates (npm run deploy:prepare). It runs once per release, before the new version starts, under an advisory lock, one transaction per file. Running it again changes nothing.
  • The server never migrates. If the database is not prepared, the new version refuses to start and the old one keeps serving.
  • Each server declares the lowest schema level it needs and refuses to start below it.

Encryption keys

ENCRYPTION_KEY encrypts two-step secrets, connector and gateway credentials, and sensitive record values. To rotate: move the old key into ENCRYPTION_KEY_PREVIOUS, set a new ENCRYPTION_KEY, run npm run fields:reencrypt, and remove the old key once its jobs finish. Losing the key without a previous copy makes stored values unreadable, so back it up apart from GitHub.

The pipeline

GitHub Actions does everything. A pull request is only checked. A merge to develop deploys stage. A merge to main deploys production after a person approves. Nothing deploys from a laptop in the normal flow, and no key file exists anywhere.

Versions and tags

  • Every deploy is a tag taken from version in the root package.json. develop gets <version>-develop.<n>. main gets <version>.
  • Raise version before the next merge. A merge that repeats a tagged version stops at the tag job. A re-run on a tagged commit reuses its tag.
  • The tag is pushed only after the deploy succeeds, so a failed deploy leaves no tag.
  • App Engine versions are named v<tag with dots as hyphens>-r<run>. Cloud Run revisions end in the same.
  • Merge develop into main with a merge commit or fast-forward, never a squash, or the stage tag disappears from history and production refuses the release.

What blocks a merge or a deploy

Code checksTypecheck. All builds (both servers, both web apps, the guide). Unit, PostgreSQL, and row-level-security tests.
Release checksThe bundle test, the console manifest test (the console stays service: console, so nobody quietly reverts its access model), and the dependency audit.
Deploy checksThe production approval, and the placeholder check: a missing REPLACE_WITH_ value stops the run before anything changes.

Pipeline setup guide

Do this once per installation. After it, every release is a merge. The workflow files in .github/workflows/ and the scripts in .github/scripts/ remain the source of truth for each step.

Never paste a secret

Not into a document, a commit, a pipeline file, an issue, or a chat. Set secrets with gh secret set or the GitHub screen, and generate each one fresh. Do not reuse a value between the main server and the console.

Step 1: The database and its four logins

You need a PostgreSQL 15+ database with pg_trgm, reachable from Google Cloud. Production and stage each get their own. The serving logins can only be granted group roles that the first deploy:prepare creates, so the order matters.

npm ci
npm run build:server
$env:DATABASE_OWNER_URL = "postgres://owner:...@host/db?sslmode=require"
npm run deploy:prepare

Now create the four logins on that database. Generate each password fresh.

create role ngo_main_system_login      login password '<generated>';  grant ngo_main_system      to ngo_main_system_login;
create role ngo_main_runtime_login     login password '<generated>';  grant ngo_main_runtime     to ngo_main_runtime_login;
create role ngo_operator_login         login password '<generated>';  grant ngo_operator         to ngo_operator_login;
create role ngo_operator_runtime_login login password '<generated>';  grant ngo_operator_runtime to ngo_operator_runtime_login;

Build five connection strings (owner plus these four, adding ?sslmode=require if needed). You will store them in Step 7. Use the provider's pooled TLS string.

Step 2: The production project, App Engine, and runtime accounts

$PROJECT = "your-project-id"
gcloud config set project $PROJECT
gcloud services enable appengine.googleapis.com cloudbuild.googleapis.com cloudscheduler.googleapis.com iamcredentials.googleapis.com iam.googleapis.com cloudresourcemanager.googleapis.com logging.googleapis.com secretmanager.googleapis.com artifactregistry.googleapis.com storage.googleapis.com
gcloud app create --region=asia-south1        # permanent: the region cannot change
gcloud iam service-accounts create ngo-main    --display-name "NGO main runtime"
gcloud iam service-accounts create ngo-console --display-name "NGO console runtime"

Each runtime account needs only roles/logging.logWriter. They never need a key file: they read their own secrets with their own identity. The production workflow stops if the App Engine app does not exist.

Step 3: Let GitHub prove who it is (workload identity)

Instead of a key file, Google Cloud trusts a short-lived token from GitHub, but only when it comes from your repository and the right branch.

$REPO = "OWNER/REPO"
$NUMBER = gcloud projects describe $PROJECT --format="value(projectNumber)"
gcloud iam service-accounts create gha-deploy --display-name "GitHub Actions deploy"
gcloud iam workload-identity-pools create github --location=global
gcloud iam workload-identity-pools providers create-oidc github-repo `
  --location=global --workload-identity-pool=github `
  --issuer-uri="https://token.actions.githubusercontent.com" `
  --attribute-mapping="google.subject=assertion.sub,attribute.repository=assertion.repository,attribute.ref=assertion.ref" `
  --attribute-condition="assertion.repository=='$REPO' && assertion.ref=='refs/heads/main'"
gcloud iam service-accounts add-iam-policy-binding "gha-deploy@$PROJECT.iam.gserviceaccount.com" `
  --role roles/iam.workloadIdentityUser `
  --member "principalSet://iam.googleapis.com/projects/$NUMBER/locations/global/workloadIdentityPools/github/attribute.repository/$REPO"

The provider's full name is the value you will store as GCP_WORKLOAD_IDENTITY_PROVIDER, and the account's email as GCP_SERVICE_ACCOUNT.

Step 8: The first run

  1. Merge to develop. Watch the stage deploy succeed and the <version>-develop.1 tag appear.
  2. Copy the stage URLs from the deploy summary into PUBLIC_BASE_URL and CONSOLE_PUBLIC_BASE_URL (stage), then run it again.
  3. Merge develop into main with a merge commit. Approve the production run.
  4. Confirm the new version holds no secret values: gcloud app versions describe <version> --service=default --project <project>. Its env_variables must not contain database URLs, TOKEN_SECRET, or ENCRYPTION_KEY.
  5. Run e2e-test.yml against stage with the selected suite.
Before the first real production deploy

Delete any App Engine version deployed before the Secret Manager change; it still holds the old plaintext values. Rotate the production database passwords and TOKEN_SECRET (that signs everyone out). Rotating ENCRYPTION_KEY is a separate procedure.

Not yet proven on a live project

The first runs will show: Playwright against a live address, npm run ci on a GitHub runner, the exact gcloud flags and deploy roles, automatic rollback in practice, and the stage Cloud Run deploy. Report any rejection to the development team rather than editing in place.

Releasing

A release is a merge. The pipeline does the rest.

  1. Bumpversion in package.json
  2. MergePR into develop
  3. Stagedeploys, tags
  4. Checkbrowser tests
  5. Promotemerge to main
  6. Approvethe prod run
  7. Verifyhealth, sign-in

Step by step

  1. Raise version in the root package.json. A merge that repeats a tagged version stops at the tag job.
  2. Open a pull request into develop. The CI gate must pass. Run npm run ci first to save a round trip.
  3. Merge it. Stage deploys on its own and the <version>-develop.<n> tag appears when it succeeds.
  4. From the Actions tab run e2e-test.yml against stage: pick the target, the suite (selected is read-only), and optionally a title filter or an address. The tests come from the branch in "Use workflow from".
  5. When stage is good, merge develop into main with a merge commit.
  6. The production run waits for the prod reviewers. Approve it.
  7. Read the deploy summary and write down the release names (the App Engine version for each service). You need them for a rollback.
  8. Check /health and /ready on the public address, sign in, and open the console.

How a release stays safe

Deploy with no trafficThe new version starts beside the live one.
Smoke test/health, /ready (proves the database answers), /sign-in. Console: /health only.
Move trafficOnly if the smoke test passed.
Check the public addressThe real URL answers.
Else move it backTraffic returns to the last good version.

Browser tests (e2e-test.yml)

SuiteWhat it runsWhere
selectedtests/e2e/post-deploy: opens the app and console sign-in pages. Signs in nothing, writes nothing.stage or prod
fullEverything in tests/e2e/specs: signs in as the seeded Riverbank members, creates donors, donations, and API keys.stage only. The workflow refuses it on prod. The stage database needs the Riverbank seed.

Specs that need something stage lacks (a mailbox, the payment fixture) skip themselves with a reason. The report is kept as an artifact for seven days. A prod run waits for the prod reviewers like a deploy does.

The manual path (rare)

Normally you never do this. If you must, from the build machine or CI:

npm ci
npm run build:server        # dist/server.js and dist/deploy.js
npm run web:build           # apps/onengo/web/dist/web/browser
$env:DATABASE_URL = '<target database>'
npm run deploy:prepare      # migrations, platform package, re-sync, profiles, shipped modules
gcloud app deploy           # only if deploy:prepare succeeded

The deploy step runs once per release from one place. Running it again is harmless. If it fails, do not deploy: a failed migration file rolls back, so the serving version keeps its schema.

Rollback and cleanup

Roll back a release

  1. Open rollback.yml in the Actions tab and choose stage or prod.
  2. Give the previous App Engine version (prod) or Cloud Run revision (stage) for the main service and for the console. The deploy summary lists them.
  3. The target environment's reviewers approve. Traffic moves.
It moves traffic only

A rollback does not undo migrations. That is why every migration must work with the release before it. The first-ever deploy has no earlier version, so there is nothing to roll back to.

Cleanup

cleanup.yml runs as a dry run on Mon, Wed, and Fri at 17:00 UTC and reports what it would delete. To delete, run it from Actions with "dry run" unticked. Both need a prod reviewer.

  • Keeps every App Engine version that has traffic, plus the newest five per service. A version whose traffic split cannot be read is kept.
  • Deletes staging-bucket files older than three days.
  • Deletes untagged Artifact Registry images.
  • The schedule only fires once the file is on the default branch.

Go-live checklist

Work down the list once, before real data goes in.

  1. Merge your branch into develop, then develop into main once the gate is green on a pull request.
  2. Create the Google Cloud project, App Engine app, service accounts, and workload identity (Steps 2 to 4).
  3. Create the database, run the first deploy:prepare, and create the four logins.
  4. Create prod and add its variables and secrets.
  5. Protect main and develop with the CI gate.
  6. Register the public addresses with the identity provider (console redirect /op/auth/callback), Google sign-in (/api/auth/oidc/callback) if used, and connectors (/api/connectors/oauth/callback).
  7. Push to main, approve, read the deploy summary, and write down the release name.
  8. Create the first console account (next section). It needs the console deployed, because the console shows you the two values to use.
  9. Rehearse a failed release once, before real data is in: deploy a build whose /health does not answer and watch traffic return.
  10. Run Cleanup (production) once as a dry run and read the report before deleting anything.
  11. Apply the alerts (next section) and run the backup drill (below).

The first console account

Operators are added in the console, on Operators. But the console only lets in someone who is already an operator, so a new installation needs one operator created by a database administrator. You do this once. Everyone after that is added in the console.

  1. Deploythe console is up
  2. Try to sign inget refused on purpose
  3. CopyProvider and Subject
  4. Run the scriptas the owner login

How it works

An operator is three small records: an account (a name), an identity (the identity provider's issuer plus the person's subject), and grants (which console actions they may use). The console signs a person in only when their issuer and subject match an active identity. There is no operator password anywhere.

Do not type the two values

The issuer must match the identity provider's token exactly, including a trailing slash, and the subject is an opaque id such as auth0|64f…. The console shows both on its sign-in page when it refuses someone, so you copy them instead of guessing.

Steps

  1. Let the person in. The console is behind Identity-Aware Proxy, so give the person the IAP access role on the console service first. Without it they never reach the console.
  2. Get refused on purpose. The person opens the console address, chooses Continue, and signs in at the identity provider with two-factor authentication. The console answers "This login is not an operator on this console" and shows Provider and Subject.
  3. Copy both values and the person's full name. Send them to the database administrator through your normal private channel.
  4. Run the script as the owner login. The owner URL is a secret: take it from where you keep it, and never paste it into a ticket, a chat, or a file. 
    psql "$DATABASE_OWNER_URL" -v ON_ERROR_STOP=1 \
  -v issuer='<Provider shown on the sign-in page>' \
  -v subject='<Subject shown on the sign-in page>' \
  -v name='<Full name of the operator>' \
  -f utilities/access/create-first-operator.sql

    The script is utilities/access/create-first-operator.sql. It runs in one transaction, creates one active account linked to that identity, grants all nine console actions (including Manage operators), and writes one operator.bootstrap row to the platform audit.

  5. Sign in again. The person now sees the whole console. They add colleagues on Operators, with a fresh sign-in for each change, and those changes are audited.

Safe to re-run

The script stops without changing anything if it is missing a value, if a value is not usable (the issuer must start with https://), or if any operator account already exists. It never creates a password and never needs a serving login.

A temporary account (one sign-in)

To give someone a single sign-in, run utilities/access/create-temporary-operator.sql instead, with the same three values. It creates an operator marked temporary. The console records the time of that first sign-in, and refuses any later sign-in for that account. The session from the first sign-in lasts up to 8 hours and cannot be extended. The row stays, so you can see when it was used.

Part of the normal deploy

The two columns this uses are in 006_operator.sql, so deploy:prepare creates them. A second sign-in is refused with "This temporary login has already been used". On Operators, a temporary account shows as used or not used yet, and its detail page shows when it first signed in.

Locally you never run this: npm run dev:setup uses utilities/seed/console-operator.sql with the sandbox sign-in (see Setup guide).

Alerts and dashboard

The platform runs no monitoring service. The server writes one JSON log line per event to stdout, which Cloud Logging reads. Entries that matter carry a fixed alert field. Keep those values stable: they are a contract with the definitions.

Server log line{"alert":"job.failed",…}
Log-based metricCounts lines with that alert.
Alert policyFires over its threshold.
Notification channelYou choose it with the product owner.
AlertSeverityMeaningFirst response
outbox.failed_permanentlyErrorA background event (email, SMS, webhook, rule, payment step) failed its fifth attempt.Read eventType, tenantId, and the error. Usually a connector setting. To retry, set that outbox_event row to pending, attempts to 0, and available_at to now.
job.failedErrorA background job stopped with an error.Read kind, jobId, and the error. The person who started it can retry once it is fixed.
http.unhandled_errorErrorA 500 from an unexpected error. Fires above 5 in 5 minutes.Search the request id in the entry's trace. A burst after a deploy points at the release: roll back.
memory.highWarningResident memory above MEMORY_ALERT_MB (default 300 of the F1's 384 MB).Look for a large import or export, or growth since a deploy. Steady load needs a larger instance class.
Nothing here applies itself

No build, test, deploy step, or server process reads the definitions. A person with Logging Admin and Monitoring Editor on the project applies them once with gcloud (alpha and beta components needed), and again after a file changes. The definitions cover production on App Engine (resource.type="gae_app"), not stage on Cloud Run.

Apply them

The nine definition files (four metrics, four policies, one dashboard) are in the deployment reference, section 8.1. Save each under its heading's file name in a working folder monitoring/ with metrics/ and policies/ inside (the folder is not part of the repository). Apply metrics first, then policies, then the dashboard.

$project = 'my-ngo-project'
Get-ChildItem monitoring/metrics/*.json | ForEach-Object {
  gcloud logging metrics create $_.BaseName --project=$project --config-from-file=$_.FullName
}
gcloud beta monitoring channels list --project=$project     # find or create the channel first
$channel = "projects/$project/notificationChannels/CHANNEL_ID"
Get-ChildItem monitoring/policies/*.json | ForEach-Object {
  gcloud alpha monitoring policies create --project=$project --policy-from-file=$_.FullName --notification-channels=$channel
}
gcloud monitoring dashboards create --project=$project --config-from-file=monitoring/dashboard.json

Do not run create twice: it makes a second policy or dashboard. To change one, use gcloud logging metrics update, gcloud alpha monitoring policies update, or gcloud monitoring dashboards update. The job, memory, and outbox policies fire on any value above 0 within 5 minutes; the HTTP policy fires above 5 in 5 minutes.

Check that an alert fires

Write a test entry. Use Bash, not PowerShell, which mangles the JSON.

gcloud logging write ngo-alert-check '{"alert":"job.failed","kind":"alert-check","message":"Alert check"}' \
  --project=<project id> --payload-type=json --severity=ERROR \
  --monitored-resource-type=gae_app --monitored-resource-labels=module_id=default,version_id=alert-check

An incident should open within minutes and close itself 30 minutes after the last entry. Repeat with memory.high at WARNING. Tune the error-rate threshold after a week of real traffic.

Backup and restore drill

Goal: prove the hosted database restores into a fresh one, the platform runs on the copy, and how long it takes. Do it on a staging database with test data.

Targets (agree with the product owner)A one-NGO proposal: recovery point 24 hours, recovery time 4 hours. A shared installation needs tighter targets and a database with point-in-time recovery.
A backup must holdThe database (provider backups plus your own pg_dump). Uploaded files (the database holds only references). ENCRYPTION_KEY with its version history. TOKEN_SECRET is not needed for data.
  1. Dump: pg_dump --format=custom --no-owner --file=ngo-backup.dump "<source DATABASE_URL>". Keep the default, which includes grants and row-level-security policies. The platform depends on both.
  2. Create a fresh, empty database on PostgreSQL 15+.
  3. On the target server create the role first (pg_dump does not copy roles): create role app_runtime nologin if missing, grant it to your server user, and create extension if not exists pg_trgm.
  4. Restore: pg_restore --no-owner --role=<target owner> --dbname="<target DATABASE_URL>" ngo-backup.dump. Errors about app_runtime or grants mean step 3 was missed.
  5. Run npm run deploy:prepare against the copy. It should apply no migrations.
  6. Start the server with the original ENCRYPTION_KEY and check: /health 200, /ready 200, a known member signs in (two-step too, which proves the key), a record list shows the same counts, an attachment downloads, a new receipt number continues with no gap or reuse, and recent audit events are present.
  7. Record the time from step 2 to the last passing check, and the age of the newest data, against the agreed targets.
  8. Drop the target database and delete the local dump. Never leave a dump of personal data on a workstation.

Write down the targets, the measured restore time, the data age, the provider and tier, any warnings, and the backup schedule now in place. If a free tier cannot meet the recovery point, schedule pg_dump to an encrypted, same-region bucket with limited access.
