OneNGO · features/passkey-authentication

Passkey technical design

WebAuthn platform passkeys as an optional sign-in method. The device keeps the private key and checks the fingerprint, face, or PIN. The server stores only the public key and a counter. An authenticator app is a separate, existing two-step check. It is not part of the passkey.

Shape

Browser

navigator.credentials.create to save, get to sign in. Converts WebAuthn base64url to the buffers the browser wants.

PasskeyService

Decides who may register, consumes the one-time challenge, and turns a verified passkey into the existing sign-in pipeline.

WebAuthn adapter

@simplewebauthn/server. Checks challenge, origin, relying-party id, user verification, and the signature.

Database

passkey_credential and passkey_challenge, owner role only. Policy flag passkey_enabled, default off.

Relying party name is OneNGO. The id is the host of PUBLIC_BASE_URL. Allowed origins are that origin, plus http://localhost:4200 when the host is localhost, plus each origin in PASSKEY_ORIGINS.

A verified passkey sign-in is assurance AAL2 with methods hwk and user. It is never AAL3. Attestation is none. New keys may be ES256 (-7) or RS256 (-257). The credential must be discoverable (residentKey: required) and user verification is required, so sign-in does not ask for an email.

Registration

The person is already signed in. A passkey cannot be the first credential for an account that has never signed in.

  1. Browser · SettingsSave a passkey on this device

    Shown only when PublicKeyCredential.isUserVerifyingPlatformAuthenticatorAvailable() is true. Name is optional, at most 60 characters. Empty becomes “Passkey”.

  3. POST /api/me/passkeys/beginSigned-in session required

    Bearer token. This path is under /api/me so the web client keeps the token. /api/auth/* is treated as signed-out.

  5. Two-step is on
    Password and authenticator code

    Checked against the stored password and the encrypted TOTP secret. The session alone is not enough.

    Two-step is off
    The live session is enough

    Same rule as first-time two-step setup.

  7. ServerIssue a registration challenge

    Refuse at 10 live passkeys. Options exclude credentials already saved. Challenge row: purpose register, this user, this organisation, expires in 300 seconds.

  9. DeviceFingerprint, face, or PIN

    navigator.credentials.create. Cancel (NotAllowedError) leaves Settings unchanged and shows no error. The private key never leaves the device.

  11. POST /api/me/passkeys/confirm · 201Consume the challenge, then verify

    One conditional update marks the challenge used. A replay, a wrong purpose, another organisation, or another user fails before verification. Then origin, relying-party id, challenge, and user verification are checked.

  13. Verified
    Store the public key

    Credential id, public key, counter, transports, device type, backup flag, name. Audit passkey.added.

    Not verified
    Nothing is stored

    “The passkey could not be saved.” Duplicate credential id and a full list of 10 are also refused.

Sign-in

  1. Browser · organisation sign-inSign in with this device

    Shown only when GET /api/auth/passkey/available?tenant= is true and this browser can use a platform authenticator. Unknown organisations answer false.

  3. POST /api/auth/passkey/optionsUsernameless challenge

    No account lookup, so the answer does not reveal who exists. allowCredentials is empty. Challenge purpose assert, no user id, 300 seconds. More than 30 attempts from one address in 15 minutes is refused.

  5. DeviceThe device offers passkeys for this site

    navigator.credentials.get, then the fingerprint, face, or PIN. Cancel returns to the card with no message.

  7. POST /api/auth/passkey/sign-inConsume, then verify

    The challenge must be unused, unexpired, purpose assert, and for this organisation. The credential id must be a live row. Signature, origin, relying-party id, and user verification are checked with the stored public key.

  9. ServerCounter must rise

    Reported counter greater than stored, except both zero, which some authenticators always report. The update is compare-and-swap on the old counter. A stall is audited as passkey.counter_rejected and refused. Other failures are passkey.sign_in_failed.

  11. Existing sign-in pipelineSame account rules as a password

    Active user and member. Organisation still has passkeys on. Evidence is method passkey, AAL2, hwk + user. Every failure the caller can see uses the same sentence, so the response does not say which check failed.

  13. No authenticator app
    Session tokens

    Access token and rotating refresh token, the same pair a password sign-in issues.

    Authenticator app is on
    Two-step ticket, 5 minutes

    { ticket }. The passkey button hides. POST /api/auth/two-step/complete checks the 6-digit code, then issues the tokens. A role that requires two-step but has no app enrolled is refused.

Authenticator app

The server does not know the app’s name and never calls it. During two-step setup it generates a TOTP secret, shows it as an otpauth:// URL, and stores the secret encrypted. The phone app and the server both compute a 6-digit code from that secret and the current 30-second window. A later check compares the typed code with the code the server just computed.

A passkey does not replace that secret. If totp_enabled is true, passkey sign-in still stops at the ticket, and adding or removing a passkey still requires the password and a current code.

Removal and policy

  1. SettingsRemove

    Same re-proof as registration when two-step is on.

  3. POST /api/me/passkeys/:id/revoke · 204Revoke and end sessions

    Sets revoked_at. Ends this person’s passkey sessions in the current organisation only. Audit passkey.revoked. A later sign-in cannot find the credential.

  5. Organisation policyPasskeys off ends passkey sessions

    tenant_auth_policy.passkey_enabled defaults to false. Turning it off calls the same session end for method passkey in that organisation. Password sessions stay. Turning passwords off still needs two protected administrators. With passkeys on and a policy of AAL2 or lower, an administrator counts toward that pair only if they hold a live passkey, or another accepted factor.

Checks and limits

CheckRule
ChallengeSingle use, 300 seconds, bound to one organisation and one purpose. Registration is also bound to the signed-in user. Consumed before cryptographic verification.
Origin and relying partyMust match the configured origins and the host of PUBLIC_BASE_URL.
User verificationRequired on registration and sign-in. A response without it is refused.
CounterMust increase, unless both the stored and reported values are 0.
Rate limit30 sign-in ceremony calls per address per 15 minutes, when the request has an address.
List size10 live passkeys per person, checked again at confirm.
Cross-organisationA challenge from one organisation cannot complete sign-in at another. A passkey whose person is not a member there is refused by the normal membership check.
Not builtNo conditional UI (passkey autofill). Rename exists on the API and is not on the Settings screen. Re-proof is the two-step password and code, not a check of how recently the session was authenticated. Removing a passkey ends passkey sessions only in the current organisation.
