1. Summary

67tables created
32migration files
~2,000lines of SQL
~20tables later altered (columns, checks)
5functions replaced or dropped later

The schema is a multi-tenant NGO platform on PostgreSQL. Almost everything tenant-owned lives behind row-level security (RLS) and the app_runtime role. A small set of tables belongs to the owner or to the operator control plane and is never reachable by tenant traffic.

Merge verdict: yes, merge. No environment has applied these files, so the history rows (the file names) that make renaming unsafe do not exist yet. Today the chain contains churn that only makes sense for an upgrade path: constraints dropped and re-added three times, functions created then dropped or replaced, a data back-fill that touches zero rows on an empty database, and a loop that rewrites every RLS policy. A baseline written in final-state form is shorter, easier to review and removes the "no 023" rule. Recommended target: 6 files (section 7). The one hard condition: confirm no shared database, including developer and CI databases you want to keep, has a kysely_migration table with these names.

2. Design model

ConcernHow the schema does it
Tenant isolationEvery tenant table has tenant_id and an RLS policy tenant_id = app_tenant(). Tenant transactions run SET LOCAL ROLE app_runtime. RLS is deliberately not FORCEd so the owner (migrations, dispatcher) can do system work.
Tenant binding (026)app.tenant_id is only trusted together with app.tenant_seal, a hash of tenant, transaction time and a secret in tenant_seal_key. Only app_bind_tenant() writes it, and only for callers that present a key registered in tenant_bind_key.
Config as dataProduct definitions (record types, workflows, rules) are rows in definition with draft/published/superseded status. The shipped base layer has tenant_id null; a tenant row is base plus its extension_patch.
Flexible recordsOne record table with a jsonb data column per type key, optimistic version, soft delete. Filters and sorts run through owner security definer functions that accept only a strict query grammar.
Money integrityDouble-entry ledger. Triggers enforce balanced entries, immutable posted rows, open periods only, lines only in the posting transaction. Receipts are numbered per series and immutable except voiding.
PrivacySensitive fields encrypted with a keyed blind index; consent and erasure logs are append-only and hold no personal values; owner functions scrub side data on erasure.
Least privilegeFour service group roles (ngo_main_runtime, ngo_main_system, ngo_operator, ngo_operator_runtime). They get no blanket table grants; cross-tenant work is exposed as named functions.
Rolling deploysschema_compatibility marks each migration additive or breaking so an older server can refuse a newer incompatible schema.

7. Merge plan

Executed. The six files in 7.2 are now in packages/platform/migrations/; the 32 old files are removed (recover them from git history). Placement differences from 7.2: api_key, member_pin, notification, tenant_auth_policy and tenant_auth_provider are in 002_identity.sql; receipt_issuer is in 003. Verified by applying old and new chains to scratch databases and diffing pg_dump output including grants: identical except (1) tenant_key_format is now validated rather than NOT VALID, and (2) the two tenant_auth_* policies use (select app_tenant()). SCHEMA_LEVEL = 6, minimums main: 5, operator: 6. Any database migrated with the old names must be recreated. The column data in section 3 was generated before the merge and still describes the same final schema.
Gate 0, before anything else: confirm no environment (staging, shared dev, CI cache, any pilot) has applied these files. Query select name from kysely_migration wherever one exists. If any database must be kept, stop: its history rows are the file names, and a merge would re-run everything on it. In that case freeze 001–033 and only add new files after them.

7.1 Rule: write final state, do not concatenate

Concatenating the 32 files would give the same churn in one file. Write each table once in its final form: fold added columns and re-created checks into create table, keep only the last version of each function, and write RLS policies directly with (select app_tenant()). Drop the 013 back-fill, the 026 policy-rewrite loop and every drop constraint / drop function.

7.3 Compatibility metadata after the merge

  • Set SCHEMA_LEVEL = 6 (or 1 for a single file).
  • Insert one schema_compatibility row per file, all additive.
  • SERVER_SCHEMA_MINIMUMS: the main server uses tables from files 001–005 (identity, ledger, organisation profile, privacy), so set main: 5; operator needs 006, so operator: 6. Section 8 explains why a self-managed install stops at 005.
  • From the first deployment on, return to the existing rule: never rename or renumber an applied file.

7.4 Steps

  1. Gate 0: confirm no applied database (above). Tag the current commit as pre-migration-merge so the old chain stays recoverable.
  2. Snapshot the reference: migrate an empty database with the old 32 files and save pg_dump --schema-only plus the RLS policies, grants and function definitions.
  3. Write the 6 files in the order above, final-state only. Keep the explanatory comments that describe why, and drop those that describe history ("migration 009...").
  4. Move the old files out of packages/platform/migrations (to an archive/ folder outside the migrator's path, or delete them; the migrator reads every *.sql in the folder).
  5. Update code: SCHEMA_LEVEL, minimums, tests, comment references, docs (section 6).
  6. Verify (section 8), then delete dev databases and rebuild artifacts.

8. Editions: hosted fleet vs self-managed (single organisation)

A self-managed customer runs one organisation and has no operator who provisions NGOs. The architecture already allows this: "One-NGO mode has a single tenant row. Same code path" (ngo-management-platform.md). The schema design does not change; the customer receives fewer migration files.

8.3 What must stay for everyone

  • Tenant binding: tenant_seal_key, tenant_bind_key, app_tenant(), app_bind_tenant(). Without them no tenant transaction can run.
  • Identity: app_user, tenant_member, role, role_assignment, refresh_token, auth_throttle, email_code, password_token, oidc_login, user_identity.
  • Organisation settings: tenant_auth_policy and tenant_auth_provider (the organisation's own SSO), organisation_profile, organisation_registration, tenant_asset. Receipts depend on the profile and registrations.
  • Compatibility metadata: schema_compatibility, so a self-managed install can upgrade safely.
  • Tenant RLS: kept. It filters nothing with one tenant, but removing it would create a second code path to test.

Earlier I suggested tenant_auth_provider might be dropped. It is needed for the organisation's own OIDC sign-in, so it stays.
