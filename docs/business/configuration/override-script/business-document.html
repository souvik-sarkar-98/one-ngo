Override scripts

Domain: configuration · Entity: override script

Implementation-independent · reconciled against backend + frontend

1. Purpose

Let an organisation add its own logic to how records are saved, checked and moved through their workflow, beyond what forms, rules and posting rules can express, without being able to break the books, permissions or another organisation's data. A script can change the record being saved, refuse a save, and propose follow-on actions: a journal entry, a new or changed related record, a notification, or a call to an approved connector. The platform checks every proposal and carries it out as part of the same save, or not at all.

2. Actors

  • Script author (holds the script-publishing permission): writes, tries and publishes scripts, and rolls them back to an earlier version. No second approval is needed, including for finance scripts.
  • Organisation administrator: everything a script author can do, plus publishing (or rolling back to) a script that acts as a role or reads ledger balances, and keeping the list of named fixed recipients. Is told about every finance-script publish and rollback.
  • Person saving a record: triggers scripts by saving, moving a record through its workflow, or pressing a custom button. Needs only permission to make that change; what a script proposes is carried out with their permissions, or with the declared role's.

3. Domain model

4. Business rules

  • A script never acts directly. Everything it proposes is checked and then carried out by the part of the platform that owns it, inside the same save. If anything is refused, nothing from that save is kept: not the record, its postings, its receipts, nor any other proposal.
  • Every journal entry a script proposes must balance to the paisa, use only accounts the script declares, fall in an open financial year, and stay within the script's per-run limit. The ledger checks again when posting, and the books check once more when the save completes.
  • A script cannot issue or change receipts, reverse entries, or open or close financial years.
  • New and changed records proposed by a script go through every check a save from the screens would, with the permissions of the person saving or of the acting role. A script cannot change the record being saved through a proposal, nor create a record of its own type from that record's own save. Changes to another record need the version the script read; if someone changed it since, the whole save is refused.
  • A script never supplies an email address or phone number. It can notify roles, people, the record's creator, a person, email or phone field of the record, or a named fixed recipient it declares. Notifications and connector calls leave only after the save completes; a failed delivery never undoes the save.
  • Connector calls go only to webhook connectors an administrator has configured and enabled, and that the script declares.
  • Inputs are read with the same permissions as the screens: a record the reader cannot see looks the same as a missing one, and protected fields are masked.
  • At most 20 proposals per run and 50 per save, nested saves included; nested saves started by scripts stop at five levels.
  • Only an organisation administrator may publish, or roll back to, a script that acts as a role or reads ledger balances. Anyone else is refused.
  • Every save that carries out proposals is recorded in the change history with each action, its script and version, the person saving, and any acting role. Each journal entry names the script and version that posted it.
  • Every publish and rollback of a finance script is recorded in the change history with the versions, the author and what changed in its proposals and code, and the organisation administrators are notified.
  • Trying a script shows the changes it would make, the inputs it would read, the actions it would propose and what would be refused, and changes nothing.
  • Unknown named recipients, accounts, connectors, roles, fields and record types are refused when the script is published.

5. User flows

Find / view

Script authors see scripts with the other configuration, their published version, draft and history. Script runs are kept for the retention period.

Create

The author writes the script, chooses its moment, declares its inputs and what it may propose, tries it against sample values or an existing record, and publishes it. The publish is refused if any reference does not exist, or if it acts as a role or reads balances and the author is not an administrator.

Update

A new draft is published as a new version. Rolling back republishes an earlier version as the newest one, under the same administrator rule. Finance-script publishes and rollbacks are recorded and announced to administrators.

Other actions

Saving a record runs its before-save, validate and after-save scripts; asking for a workflow step also runs its workflow-guard scripts; a record action can run a custom-button script whose changes are saved as an update. Administrators keep the named fixed recipients in the organisation settings.

7. Out of scope / non-goals

  • Scripts that look up data they did not declare, or call back into the platform while running.
  • Deleting records, reversing entries, issuing receipts or changing financial years from scripts.
  • A daily posting ceiling per script (only the per-run maximum exists).
  • Running the follow-on saves of proposed records while trying a script.
  • A second approval for finance scripts.
  • Calculated-field, scheduled-job, report-shaping and payment-matching moments.
